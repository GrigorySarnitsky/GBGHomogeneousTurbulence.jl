Forcing

GBGHomogeneousTurbulence.Forcing — Module
Forcing

The interchangeable energy-injection strategies — one implementation each serving both the velocity and the scalar through tensor-order-generic field operators.

Every strategy is an AbstractForcing. It enters the time step through four functions, each called at its own point of the step and each doing nothing unless the strategy defines a method for it (in software terms, hooks: functions a framework calls at fixed points, which a plug-in may supply):

  • steady_linear_rate — a steady linear rate, folded into the integrating factor once, when the generator is built.
  • prepare_forcing! — advance the strategy's evolving state, once per step, before the Runge–Kutta stages.
  • add_forcing_source! — add a source term at each stage.
  • project_forcing! — project or rescale the field after the step.

A strategy that has an evolving state gets it once, from initial_forcing_state.

The strategies; each but NoForcing acts on a band, an annulus of integer Fourier shells:

  • NoForcing — leave the field undriven.
  • Linear — a fixed linear rate on the band.
  • ConstantPower — a band amplitude re-solved each stage to hold the injection rate; the velocity default.
  • VarianceController — drive the field's variance to a target by feedback.
  • VarianceRescaling — hold the band's or the whole field's variance (over) by deterministic rescaling, at first order.
  • StochasticOU — a random force correlated over a finite time, independent of the flow (Eswaran & Pope); its evolving state is a StochasticOUState.

The stationary state a run predicts for its forcing, from provisional values:

  • kinetic_energy_in_box_units, band_energy_fraction — the predicted kinetic energy in box units $\tilde{k}$ and the band's predicted share of it.

Construction and persistence:

  • DeferredForcing — the keyword form of a strategy, built into the concrete strategy once the Simulation has built the domain; a construction-time object that no step calls.
  • write_forcing / read_forcing — a strategy's HDF5 persistence: its defining parameters as one self-describing group (available once HDF5 is loaded).

The velocity and the scalar are forced independently: FlowConditions — the Generator parameter record bundling the viscosity, the Schmidt number, and the two forcings — takes a separate velocity_forcing and scalar_forcing, so a run can force one, both, or neither.

source

Forcing strategies

The forcing supertype and its concrete strategies, grouped by the route each takes through the step — which is what decides whether it preserves the scheme's order. Linear supplies a steady rate folded into the integrating factor, exactly and for free. ConstantPower and VarianceController supply rates that track the state, so they enter the right-hand side at every Runge–Kutta stage. VarianceRescaling rescales after the step, which is operator splitting and first-order by construction. At every stage StochasticOU adds a random force that does not depend on the flow. One implementation serves either the velocity or the scalar.

GBGHomogeneousTurbulence.Forcing.AbstractForcing — Type
AbstractForcing

This is the supertype of the energy-injection strategies — the interchangeable ways a run drives its velocity or its scalar.

A strategy enters the time step through four functions and defines whichever it needs; each does nothing by default. The generator calls the first once, when it is built, and a step calls the other three in a fixed order:

  • steady_linear_rate — once, when the generator is built: return a per-mode rate that stays fixed for the whole run, which the scheme folds exactly into the integrating factor.
  • prepare_forcing! — once, before the Runge–Kutta stages, the intermediate evaluations a scheme makes within one step: advance the strategy's own evolving state, such as a stochastic forcing's random process. initial_forcing_state creates that state and the run's ResolvedFields holds it.
  • add_forcing_source! — at every stage: add a source term to the right-hand side.
  • project_forcing! — once, after the completed step: project or rescale the advanced field.

A forcing term divides as the rest of the equation does: its steady linear part joins the viscous term in the integrating factor and is integrated exactly; the remainder joins the explicit right-hand side and is evaluated at every Runge–Kutta stage. A single strategy may use both.

Which part a rate may join is decided by steadiness in time, not by linearity in the field. The integrating factor holds a rate fixed for the whole step, so a rate re-solved from the state must go through add_forcing_source! instead; freezing it in the integrating factor would drop the scheme to first order.

The rate function is handed neither the field nor the time, so the rate it returns cannot depend on the state: it is steady by construction.

Each mutating function returns the argument it mutated: add_forcing_source! the right-hand side, project_forcing! the field. The function prepare_forcing! returns nothing, having advanced the state it was handed in place.

The four run inside the time loop, which is allocation-free at field scale, so a strategy allocates whatever scratch it needs once, when it is built, and its methods touch only that scratch and the arguments they are given.

One instance per forced field, for a strategy with mutable bookkeeping

A strategy that mutates its own fields as it runs must not drive both fields from one instance, or their bookkeeping is conflated; FlowConditions throws an ArgumentError rather than let that happen. Every strategy here may be shared: none carries anything from one call to the next, since what a strategy evolves lives in the run's state, one entry per field, and its scratch is overwritten before each use.

GBGHomogeneousTurbulence.Forcing.Linear — Type
Linear(domain; rate, lowest_shell = 1, highest_shell = 2)

Linear (negative-damping) forcing $f = A \cdot \texttt{field}$ in a low-wavenumber band (a band-limited variant of the forcing of Lundgren (2003), which acts at every wavenumber), built on the FixedDomain domain. The rate is folded into the integrating factor, so the forced band modes grow at net rate $A - D\lvert\boldsymbol{\kappa}\rvert^{2}$ ($D$ the field's diffusivity).

It is the only strategy taking that route — exactness there is a statement about a steady $A$ — which makes it the cheapest forcing here, at no per-stage reduction and no host readback.

Arguments

  • domain — the FixedDomain the band is built on.
  • rate — the fixed linear rate $A$. A positive value amplifies the field. The deferred form may leave it out, and a run then supplies $A = \varepsilon/(2 k_{\mathrm{band}})$, with $k_{\mathrm{band}}$ the kinetic energy held in the forced band, from the state predicted_stationary_state returns. The rate is fixed, not fed back from the measured state, so the run settles near that state rather than exactly at it.
  • lowest_shell = 1, highest_shell = 2 — the forced band, as integer shells in units of the box's fundamental $2\pi/L$. A finite band reaching past the dealias cutoff draws a warning: the dealiasing keeps those modes empty, so the forcing adds nothing there. highest_shell = Inf lifts the band limit: every retained mode but the mean is forced, on any grid, and this is Lundgren's forcing itself — the form a physical-space code applies.

References

  • Lundgren, T. S. (2003). Linearly forced isotropic turbulence. CTR Annual Research Briefs, 461–473. (No DOI.)

Fields

  • band — the band-pass kernel, evaluated per mode where used rather than stored, as is the rate on the same edges.
  • rate — the fixed linear rate $A$.
  • lowest_shell, highest_shell — the forced band's shell bounds: the parameters band is derived from.

GBGHomogeneousTurbulence.Forcing.ConstantPower — Type
ConstantPower(domain; injection_rate, lowest_shell = 1, highest_shell = 2)

Constant-injection-rate forcing, built on the FixedDomain domain: a banded linear forcing $f = A \cdot \texttt{field}$ on the integer shells lowest_shell to highest_shell (in units of the box's fundamental $2\pi/L$; default 1–2), whose rate $A$ is re-solved at every stage so the injection rate holds the injection_rate. A linear rate injects at $2 A k_{\mathrm{band}}$, with $k_{\mathrm{band}}$ the band's own observable, so the rate that holds it is

\[A = \frac{\texttt{injection\_rate}}{2 k_{\mathrm{band}}}.\]

In stationarity the injection balances dissipation, so injection_rate is the value $\varepsilon$ relaxes to in the stationary mean — chosen to agree with the diagnostics — the rate $\varepsilon$ for the velocity (measured by dissipation) and $\varepsilon_\varphi$ for the scalar (by scalar_dissipation). The keyword names the kind of quantity it is — a rate, where VarianceRescaling's target is an amplitude.

Since that amplitude is re-solved from the state, it enters the right-hand side at every stage rather than the integrating factor, where freezing it would cost the scheme its order. Like Linear it is a per-mode multiple of the field, so it preserves a solenoidal velocity.

Arguments

  • domain — the FixedDomain the band is built on.
  • injection_rate — the rate at which energy (for the velocity) or scalar variance (for the scalar) is injected; not an instantaneous dissipation the forcing measures or clamps. A deferred velocity forcing may leave it out, and the run then supplies its stationary $\varepsilon$ (see DeferredForcing).
  • lowest_shell = 1, highest_shell = 2 — the forced band, as integer shells in units of the box's fundamental $2\pi/L$. A finite band reaching past the dealias cutoff draws a warning: the dealiasing keeps those modes empty, so the forcing adds nothing there. highest_shell = Inf forces every retained mode but the mean, on any grid: the band-free linear forcing of Lundgren (2003) that physical-space codes apply, with its rate re-solved to hold the injection.
An empty band is left alone, not driven infinitely hard

The rate $A$ diverges as the band's own value goes to zero — its energy for the velocity, its variance for the scalar — which is reachable: a scalar seeded with nothing in the forced shells, or the step after a VarianceRescaling(over = :total) zeroed the band. Below a machine-roundoff floor on the band's observable — measured relative to the whole field's, so the test is invariant under a uniform rescaling of the field — the amplitude is set to zero, and an empty band stays empty rather than taking an unbounded kick; seed content in the band if a run needs the forcing to take hold.

References

  • Lundgren, T. S. (2003). Linearly forced isotropic turbulence. CTR Annual Research Briefs, 461–473. (No DOI.)

Fields

  • band — the band-pass kernel, evaluated per mode where used: the per-stage source both weights the band observable with it and convolves against it, so no indicator array is stored.
  • injection_rate — the held rate.
  • lowest_shell, highest_shell — the forced band's shell bounds: the parameters band is derived from.

GBGHomogeneousTurbulence.Forcing.VarianceController — Type
VarianceController(domain; target, gain = 1, turnover_time = nothing,
                   lowest_shell = 1, highest_shell = 2)

Hold the field's variance at target by feedback — the kinetic energy $k$ for the velocity, $\langle\varphi^{2}\rangle$ for the scalar — with the constant-$k$ controller of Bassenne et al. (2016).

Prefer it to VarianceRescaling whenever accuracy in time matters, which is nearly always: it enters the right-hand side as a smooth rate the scheme integrates and keeps its order, where a rescaling is a post-step projection capping the iteration at first order.

The rate is the marginal law $A = \varepsilon/2k_{\mathrm{band}}$, with $k_{\mathrm{band}}$ the variance held in the forced band, plus a proportional restoring term:

\[A(\boldsymbol{\kappa}, t) = \frac{\varepsilon(t) - G[k(t) - k_\infty]/t_\ell}{2k_{\mathrm{band}}(t)} \quad\text{in the band, } 0 \text{ outside,}\]

with $k_\infty$ the target, $G$ the gain and $t_\ell$ the turnover_time, so that $\mathrm{d}k/\mathrm{d}t = -G(k - k_\infty)/t_\ell$ exactly: the variance relaxes exponentially to a stable attractor with settling time $t_\ell/G$.

The limit gain = 0 is the bare marginal law, and it is allowed: exact reinjection of the instantaneous $\varepsilon$ makes $\mathrm{d}k/\mathrm{d}t = 0$, so $k$ is conserved at its initial value and target never enters the rate. Every level is then a neutral equilibrium — the reinjection cancels the cascade's own restoring response, which ConstantPower's fixed injection retains — so discrete integration bias accumulates uncorrected (about 1% of $k$ per 1000 steps, measured at $24^3$ in Float64; a Float32 run's roundoff bias is larger and unmeasured), and nothing ever restores it.

The two variances there are not interchangeable: $k$ is the whole field's, the one held; $k_{\mathrm{band}}$ the forced band's, dividing out because the forcing injects only there. An empty band is left alone rather than divided by $\sim 0$ (the floor ConstantPower documents), so seed content in the band if the run depends on the controller taking hold.

Arguments

  • domain — the FixedDomain the band kernel is built on; without it the constructor returns the deferred form, a DeferredForcing.
  • target — the whole-field variance $k_\infty$ to hold, in the field's own convention: the kinetic energy for the velocity, $\langle\varphi^{2}\rangle$ for the scalar. The deferred velocity form may leave it out, and the run then supplies its stationary $k$.
  • gain = 1 — the dimensionless gain $G$. A larger gain relaxes faster; Bassenne et al. report $O(1-10)$, and the default sits at that range's gentle end so the controller perturbs the dynamics least. 0 is the bare marginal law above.
  • turnover_time = nothing — the large-eddy turnover time $t_\ell = 2k_\infty/(3\varepsilon_\infty)$ (Bassenne's convention: $\tfrac{2}{3}$ of the run layer's eddy-turnover unit $k/\varepsilon$). Left at nothing it is computed for you from that formula. A Simulation uses the state it predicts; built on a domain, the controller takes $\varepsilon_\infty = (k_\infty/\tilde{k})^{3/2}/L$ with $\tilde{k}$ its band's placeholder kinetic energy in box units (kinetic_energy_in_box_units), and refuses a band that model does not cover. A run that sets $\nu$ against a very different regime should pass its own value. The derivation reads target as a kinetic energy, so it is valid only for the velocity: a controller left at the default and handed to FlowConditions as a scalar_forcing with a positive gain is refused there — a scalar variance is not an energy, and the derived settling time would depend on the scalar's amplitude unit, breaking the scalar equation's exact linearity in $\varphi$ (at gain = 0 the settling time never enters the dynamics and the marginal law stays legal). Driving the scalar, pass the flow's turnover time $2k/(3\varepsilon)$ explicitly.
  • lowest_shell = 1, highest_shell = 2 — the forced band, in integer shells of $2\pi/L$. A finite band reaching past the dealias cutoff draws a warning: the dealiasing keeps those modes empty, so the forcing adds nothing there. highest_shell = Inf forces every retained mode but the mean, on any grid: the band-free linear forcing of Lundgren (2003) that physical-space codes apply, where $k_{\mathrm{band}} = k$ — the form Bassenne et al. designed the controller in.

This controller is the turbulence counterpart of the Berendsen thermostat of molecular dynamics (Berendsen et al. 1984), which relaxes the temperature by the same law. It shares that thermostat's known cost: the held quantity's fluctuations are removed, since $k$ relaxes to $k_\infty$ and then stays there, and the flow's variability moves into $\varepsilon$ and the injected power. Per-step rescaling, the cruder thermostat, is VarianceRescaling here. Keeping the fluctuations of $k$ takes an extended-variable thermostat, that of Nosé (1984) and Hoover (1985), whose rate is a dynamical variable with an equation of motion of its own.

The settling time, not the gain, is the physical parameter

Only the ratio $t_\ell/G$ is observable: it is how long the variance takes to return after a disturbance. The two are kept separate because that is how the source states them.

References

  • Bassenne, M., Urzay, J., Park, G. I. & Moin, P. (2016). Constant-energetics physical-space forcing methods for improved convergence to homogeneous-isotropic turbulence with application to particle-laden flows. Phys. Fluids 28, 035114.
  • Berendsen, H. J. C., Postma, J. P. M., van Gunsteren, W. F., DiNola, A. & Haak, J. R. (1984). Molecular dynamics with coupling to an external bath. J. Chem. Phys. 81, 3684–3690.
  • Nosé, S. (1984). A unified formulation of the constant temperature molecular dynamics methods. J. Chem. Phys. 81(1), 511–519.
  • Hoover, W. G. (1985). Canonical dynamics: Equilibrium phase-space distributions. Phys. Rev. A 31(3), 1695–1697.
  • Lundgren, T. S. (2003). Linearly forced isotropic turbulence. CTR Annual Research Briefs, 461–473. (No DOI.)

Fields

  • band — the band-pass kernel, evaluated per mode where used; the controller convolves against it and stores nothing.
  • target, gain, turnover_time — $k_\infty$, $G$ and $t_\ell$.
  • turnover_time_derived — true when $t_\ell$ came from the kinetic-energy default rather than the caller; FlowConditions refuses such a controller as a scalar_forcing at a positive gain.
  • lowest_shell, highest_shell — the forced band's shell bounds: the parameters band is derived from.

GBGHomogeneousTurbulence.Forcing.VarianceRescaling — Type
VarianceRescaling(domain; target, over, lowest_shell = 1, highest_shell = 2)

The deterministic rescaling forcing of Sullivan, Mahalingam & Kerr (1994), built on the FixedDomain domain: after each step the in-band Fourier modes — the integer shells lowest_shell to highest_shell, in units of the box's fundamental $2\pi/L$ — are rescaled by a single factor that holds target. The rescale is per-mode, so a divergence-free velocity stays divergence-free.

Prefer VarianceController for a run whose accuracy in time matters, which is nearly always. It holds the same quantity through a rate the scheme integrates and keeps the scheme's order; this one is applied after the step and costs it (see the caveat below). It is kept because it is a published method a reader may need to reproduce, and because holding a band's value exactly is occasionally what is wanted.

Which observable is held follows from the field, chosen to agree with the diagnostics: the kinetic energy $\tfrac{1}{2}\langle\lvert\boldsymbol{u}\rvert^{2}\rangle$ for the velocity (kinetic_energy), the scalar variance $\langle\varphi^{2}\rangle$ for the scalar (scalar_variance) — each the field's $L^{2}$ observable, the $\tfrac{1}{2}$ belonging to the kinetic energy's definition rather than to the field being a vector.

Arguments

  • domain — the FixedDomain the band kernel is built on.
  • target — the value held, in the field's own observable above. The deferred form may leave it out, and a run then supplies it: its stationary $k$ for over = :total, and the band's predicted $k_{\mathrm{band}}$ for over = :band. That prediction takes the band's share of $k$ to be the one over = :total holds on the same band: both rescale the same modes, and they are taken to reach the same stationary flow.
  • over — where the target applies, :band or :total. It is required because the right choice depends on what the run is calibrated against. A Simulation deriving $\nu$ derives it from the assumed kinetic energy, so a VarianceRescaling given to it must be :total, or that calibration stops holding; where nothing calibrates against $k$, :band is the gentler clamp. The two modes differ in which quantity a run may no longer measure:
    • :band holds the band's own value. The whole-field value then floats, oscillating about its mean as the band feeds the cascade. On the default shells 1–2 — the energy-containing range — most of $k$ is held rather than free, though it remains a measurable.
    • :total rescales the band to absorb the whole-field deficit, so the whole-field value equals target. For the velocity this pins $u'$ and with it the scale of $\mathrm{Re}_\lambda$ (whose value still fluctuates with the instantaneous dissipation). Here $k$ is what the forcing sets and the band is free.
  • lowest_shell = 1, highest_shell = 2 — the rescaled band, as integer shells in units of the box's fundamental $2\pi/L$. A finite band reaching past the dealias cutoff draws a warning: the dealiasing keeps those modes empty, so the forcing adds nothing there. With highest_shell = Inf the band is every retained mode but the mean, on any grid, and the two modes of over coincide — the mean holds nothing in a field started without one — so a single factor rescales the whole field: the rescaling a physical-space code applies.

Sizing the rescale reduces the field to a number, so each step blocks on one device-to-host transfer: the band and whole-field observables ride a single fused traversal, in either mode.

First order in time, and two extremes worth knowing

This is the one forcing that costs the scheme its order, by construction rather than by defect: the rescale is applied after the step, which is Lie–Trotter operator splitting — the step's map and the rescale's map composed one after the other, a composition whose error is $O(\Delta t)$ regardless of how accurate either map is alone — so it is first-order however good the scheme is. Measured on the third-order IFLowStorageRK3: 1.02 here, against 3.01 for Linear, ConstantPower, VarianceController and an unforced run. (A stochastic forcing is outside that comparison — it has no classical order to lose.) Molecular dynamics reached the same conclusion about the same manoeuvre — per-step rescaling is the deterministic (Berendsen) limit of stochastic velocity rescaling, with no conserved quantity and no well-defined ensemble except in limiting cases (Bussi, Donadio & Parrinello 2007) — and the fix is to extend the dynamics with feedback rather than project after the fact.

Two configurations also behave sharply. Under :total, if the value outside the band alone exceeds target, the band is zeroed — the closest reachable state, and the most violent intervention the rescale can make. At the other end an empty band is left alone rather than divided by ~0, so it stays empty instead of being driven to target. Seed content in the band if a run depends on the clamp taking hold.

References

  • Sullivan, N. P., Mahalingam, S. & Kerr, R. M. (1994). Deterministic forcing of homogeneous, isotropic turbulence. Phys. Fluids 6(4), 1612–1614.
  • Bussi, G., Donadio, D. & Parrinello, M. (2007). Canonical sampling through velocity rescaling. J. Chem. Phys. 126, 014101.

Fields

  • band — the band-pass kernel selecting the rescaled shells.
  • target — the held value.
  • over — :band or :total.
  • lowest_shell, highest_shell — the forced band's shell bounds: the parameters the band kernel is derived from, kept so the strategy remains its own record.

GBGHomogeneousTurbulence.Forcing.StochasticOU — Type
StochasticOU(domain; forcing_variance, correlation_time, lowest_shell = 1,
             highest_shell = 2, seed = rand(Int))

The stochastic forcing of Eswaran & Pope (1988), built on the FixedDomain domain: a random term, correlated over a finite time, added to the right-hand side on a band of low wavenumbers.

Use it when the forcing must not depend on the flow it drives. Every other strategy here measures the field it forces and sets its amplitude from that measurement; this one draws from a random process instead. The price is that the energy it injects fluctuates rather than being held — take ConstantPower or VarianceController when a run needs the injection or the variance held at a value.

Its strength is forcing_variance, the stationary mean square $\sigma^{2} = \langle\lvert\boldsymbol{f}\rvert^{2}\rangle$ of the term added: an acceleration when it drives the velocity, a rate of change of $\varphi$ when it drives the scalar. It is not the variance of the field itself, which is what VarianceController holds.

The forcing lives on the band's Fourier modes — the integer shells lowest_shell to highest_shell in units of the box's fundamental $\kappa_0 = 2\pi/L$:

\[\boldsymbol{f}(\boldsymbol{x}, t) = \sum_{\boldsymbol{\kappa}} \boldsymbol{a}_{\boldsymbol{\kappa}}(t) e^{\mathrm{i}\boldsymbol{\kappa}\cdot\boldsymbol{x}},\]

where each amplitude $\boldsymbol{a}_{\boldsymbol{\kappa}}$ is an independent complex Ornstein–Uhlenbeck process with correlation time $T_L$. When the forced field is the velocity, each amplitude is drawn transverse to its own $\boldsymbol{\kappa}$, so the force is divergence-free. The variance $\sigma^{2}$ is shared equally among the band's modes and their independent components.

Once per step every amplitude takes the process's exact transition over the step $\Delta t$,

\[\boldsymbol{a}_{\boldsymbol{\kappa}} \leftarrow \alpha \boldsymbol{a}_{\boldsymbol{\kappa}} + \sqrt{1 - \alpha^{2}} \boldsymbol{\xi}_{\boldsymbol{\kappa}}, \qquad \alpha = e^{-\Delta t / T_L},\]

with $\boldsymbol{\xi}$ a fresh draw from the stationary distribution, so the statistics are exact for any step, a step the CFL condition varies included. The process starts from a stationary draw rather than from zero.

How much energy that injects depends on how the force and the field line up. Over a correlation time the force builds the very velocity it then does work against, so while $T_L$ is short against the large-eddy turnover time the mean injection rate is close to $\sigma^{2} T_L$ into the kinetic energy $k$, and to $2\sigma^{2} T_L$ into the scalar variance $\langle\varphi^{2}\rangle$. Both are estimates the run drifts around, not values anything holds: choose forcing_variance from the dissipation rate the run should sustain, and measure what it actually injects.

The forcing is held fixed over a step and added at every stage, as add_forcing_source! does for every additive source. For a given sequence of amplitudes the field then advances at the scheme's order, but the forcing itself is resolved in time only step by step, so $T_L$ should span many steps.

Arguments

  • domain — the FixedDomain of the run this forcing drives; without it the constructor returns the deferred form, a DeferredForcing.
  • forcing_variance — the stationary mean square $\sigma^{2}$ of the added term, as above. A deferred velocity forcing may leave it out, and the run then supplies $\varepsilon/T_L$, the variance whose estimated injection matches its stationary $\varepsilon$.
  • correlation_time — the correlation time $T_L$ of each amplitude. The deferred form takes either it or correlation_time_in_box_units, a multiple $\tilde{T}_L$ of $(L^{2}/\varepsilon)^{1/3}$ that a run converts once into $T_L = \tilde{T}_L (L^{2}/\varepsilon)^{1/3}$ from its predicted $\varepsilon$; exactly one of the two.
  • lowest_shell = 1, highest_shell = 2 — the forced band, as integer shells in units of $\kappa_0$; every mode of the band must lie inside the dealias cutoff, so the Inf the field-multiplying strategies accept is refused here.
  • seed — fixes the random stream; left out, it is drawn from the run's rng when a Simulation builds the forcing, and from the global stream (rand(Int)) when the forcing is built on a domain. A velocity and a scalar forcing given the same seed still draw independent streams.

The process lives in the run's state, not in this strategy. A run keeps it as a StochasticOUState — the modeled entry of its ResolvedFields — held on a small grid of its own over the same box, large enough to carry the band and no larger, so the whole forcing costs a few kilobytes and runs no transform at the resolution of the run. A checkpoint of the state therefore resumes the same realization. This strategy holds its parameters and the scratch of one draw, so one instance may drive both fields.

A ResolvedFields built by hand that carries no state for this forcing is refused: preparing it throws an ArgumentError rather than leave the run unforced without saying so. A Simulation builds it for you.

The band must lie inside the dealias cutoff

A forcing that multiplies the field injects nothing where the dealiasing mask holds the modes empty, but this forcing is added after the mask and would fill them. Construction therefore throws an ArgumentError for a band reaching past the cutoff, where the other strategies only warn.

References

  • Eswaran, V. & Pope, S. B. (1988). An examination of forcing in direct numerical simulations of turbulence. Computers & Fluids 16, 257–278.

Fields

  • forcing_variance, correlation_time, seed, lowest_shell, highest_shell — the parameters above.
  • companion — the coarse FixedDomain over the same box the process is held on: the smallest grid whose modes cover the band, so the whole forcing costs a few kilobytes and no transform at the run's own resolution.
  • band — the shell band, as a kernel on the companion.
  • velocity_scratch, scalar_scratch — one draw's scratch for each kind of forced field: a physical and a spectral companion field, the host array the draw is made in, and the scale that turns a unit-variance draw into the stationary distribution.
  • rng — the random-number generator, reseeded before every draw from the seed, the state's draw count, and which field is being forced, which is what makes a velocity and a scalar forcing of one seed independent. Scratch, not state.

Forcing state

What a strategy evolves lives in the run's state rather than in the strategy, so saving the state saves it too. StochasticOU is the only strategy here that carries such a state.

GBGHomogeneousTurbulence.Forcing.StochasticOUState — Type
StochasticOUState

A StochasticOU forcing's evolving state holds two things: the force itself, as a field in spectral representation on the forcing's companion grid, and the number of increments drawn so far. It is created by initial_forcing_state, advanced in place every step by prepare_forcing!, and kept by a run as the modeled entry of ResolvedFields for the forced field. There is no reason to build one by hand.

Holding the force as an ordinary field is what keeps the rest simple. The draw is made real-valued and then transformed, so its spectrum satisfies the reality condition by construction; the transverse projection is GBGPeriodicFields'; and the state is saved by that package's field persistence.

The amplitudes are physical — the coefficients of $e^{\mathrm{i}\boldsymbol{\kappa}\cdot\boldsymbol{x}}$ in the force, with no transform normalization — so neither the state nor a checkpoint of it depends on either grid's size. The draw count, with the forcing's seed, fixes every later draw.

Fields

  • process — the force in spectral representation on the companion grid.
  • draws — the number of increments drawn so far, the stationary start included.

The stationary-state model

Two functions predict the stationary state a forcing drives: the kinetic energy in box units $\tilde{k}$ (scaled by the box side and the dissipation rate) and the forced band's share of it, both provisional placeholders until they are measured.

GBGHomogeneousTurbulence.Forcing.kinetic_energy_in_box_units — Function
kinetic_energy_in_box_units(forcing; reynolds_box = nothing, reynolds_taylor = nothing)

The kinetic energy a flow driven by forcing holds in its stationary state, in box units, $\tilde{k} \equiv k/(\varepsilon L)^{2/3}$: the kinetic energy $k$ over the energy $(\varepsilon L)^{2/3}$ of a Kolmogorov eddy the size of the box, with $L$ the box side and $\varepsilon$ the dissipation rate. Its $3/2$ power is the large-eddy length $k^{3/2}/\varepsilon$ as a fraction of the box side. It is what a run predicts its state with: given $k$, the dissipation is $\varepsilon = (k/\tilde{k})^{3/2}/L$, and given $\varepsilon$, the energy is $k = \tilde{k} (\varepsilon L)^{2/3}$. Its companion band_energy_fraction is the share of $k$ held in the forced band.

Arguments

  • forcing — the velocity forcing, built or in its deferred keyword form. The value depends on its strategy, its band and, for VarianceRescaling, on over, but not on its strength.
  • reynolds_box, reynolds_taylor — the Reynolds number the value is wanted at: exactly one of the box Reynolds number $\varepsilon^{1/3}L^{4/3}/\nu$ (reynolds_box) and the Taylor-microscale $\mathrm{Re}_\lambda$ (reynolds_taylor).

Returns a Float64. An unforced flow, a forcing without a band, a band that does not start at shell 1 and a band ending at shell 1 have no value and throw an ArgumentError, as do both or neither Reynolds number.

Placeholder values

The values are provisional, the same for every strategy, and do not yet depend on the Reynolds number: the keyword is checked and then has no effect. They are 0.72 for shells 1–2, 0.56 for shells 1–4 and 0.47 for every mode but the mean, measured in this package's first sweep, and interpolated linearly in the reciprocal of highest_shell between them. A measured table per strategy and band replaces them.

GBGHomogeneousTurbulence.Forcing.band_energy_fraction — Function
band_energy_fraction(forcing; reynolds_box = nothing, reynolds_taylor = nothing)

The share of the kinetic energy a flow driven by forcing holds in its forced band, in its stationary state: $k_{\mathrm{band}}/k$, with $k_{\mathrm{band}} = \tfrac{1}{2}\sum_{\text{band}} \lvert\hat{\boldsymbol{u}}\rvert^{2}$ over the shells lowest_shell to highest_shell. A run uses it to set a strength that is stated through the band: the rate of Linear, $A = \varepsilon/(2 k_{\mathrm{band}})$, and the target of VarianceRescaling(over = :band), which is $k_{\mathrm{band}}$ itself. The band that holds everything but the mean (highest_shell = Inf) has the fraction 1.

Arguments

  • forcing — the velocity forcing, built or in its deferred keyword form, as for kinetic_energy_in_box_units. For VarianceRescaling(over = :band) the fraction is the one over = :total holds on the same band: both rescale the same modes, one holding the band and the other the whole field, so they are taken to reach the same stationary flow.
  • reynolds_box, reynolds_taylor — exactly one: the Reynolds number the value is wanted at.

Returns a Float64, and refuses what kinetic_energy_in_box_units refuses.

Placeholder values

Until it is measured, the fraction is the inertial-range estimate: the energy $\tfrac{3}{2}C_K \varepsilon^{2/3}\kappa_{\mathrm{c}}^{-2/3}$ above the band's outer edge $\kappa_{\mathrm{c}} = (h + \tfrac{1}{2}) 2\pi/L$, with $h$ the highest_shell and $C_K = 1.5$, subtracted from $k$, so that $k_{\mathrm{band}}/k = 1 - \tfrac{3}{2}C_K/[\tilde{k}(2\pi(h + \tfrac{1}{2}))^{2/3}]$ with $\tilde{k}$ the placeholder kinetic energy in box units. It gives about 0.50 for shells 1–2 and 0.57 for shells 1–4, and it does not depend on the Reynolds number.

Deferred forcing

This section documents the domain-free deferred form a strategy's constructor returns, which is materialized into a concrete forcing once the domain exists.

GBGHomogeneousTurbulence.Forcing.DeferredForcing — Type
DeferredForcing

A DeferredForcing is a forcing named before its domain exists. It is built into the concrete AbstractForcing once the FixedDomain exists, which Simulation does for you. A forcing argument therefore accepts either a ready-built AbstractForcing (from the domain-taking constructor) or a DeferredForcing.

These keyword constructors take no domain, and each returns a DeferredForcing holding its keywords:

ConstantPower(; injection_rate = nothing, lowest_shell = 1, highest_shell = 2)

VarianceController(; target = nothing, gain = 1, turnover_time = nothing,
                   lowest_shell = 1, highest_shell = 2)

VarianceRescaling(; target = nothing, over, lowest_shell = 1, highest_shell = 2)

StochasticOU(; forcing_variance = nothing, correlation_time = nothing,
             correlation_time_in_box_units = nothing, lowest_shell = 1,
             highest_shell = 2, seed = nothing)

Linear(; rate = nothing, lowest_shell = 1, highest_shell = 2)

Only the deferred form may leave its target out, because only a run can supply it. A velocity forcing built by Simulation then takes the quantity it controls from the stationary state the run is set up for:

  • ConstantPower its injection_rate, from the dissipation rate $\varepsilon$;
  • VarianceController and VarianceRescaling(over = :total) their target, from the kinetic energy $k$ — or, bound to the scalar, from the scalar's stated variance — and a controller its turnover_time, from the flow's $2k/(3\varepsilon)$ whichever field it drives;
  • VarianceRescaling(over = :band) its target, from the predicted energy in the band $k_{\mathrm{band}}$;
  • Linear its rate, from $A = \varepsilon/(2 k_{\mathrm{band}})$, the rate that injects $\varepsilon$;
  • StochasticOU its forcing_variance, from $\varepsilon/T_L$ — the variance whose injection $\sigma^{2} T_L$ matches $\varepsilon$ while $T_L$ is short.

The state, and $k_{\mathrm{band}}$ with it, is the one predicted_stationary_state returns. The deferred StochasticOU may state its correlation time in box units, as a multiple of $(L^{2}/\varepsilon)^{1/3}$, which the run converts once into the constant time $T_L$ the strategy holds; its seed, left out, is drawn from the run's rng. A scalar forcing takes only a whole-field target from the run, the scalar's stated variance, since no scalar stationary state is modelled; anything else it states. Otherwise the keywords and defaults are those of the domain-taking forms documented on each strategy.

Examples

# The run supplies the injection rate from the dissipation it is set up for:
sim = Simulation(grid_points_per_axis = 64, kinetic_energy = 1.5,
                 velocity_forcing = ConstantPower())

# Or state it, and the forcing's target is the run's state:
sim = Simulation(grid_points_per_axis = 64,
                 velocity_forcing = ConstantPower(injection_rate = 0.4))

# Or build it directly, once the domain is in hand:
domain = FixedDomain(; grid_points_per_axis = 64, side_length = 2π,
                     dealiasing = TwoThirds(), element_type = Float64,
                     array_family = Array)
forcing = ConstantPower(domain; injection_rate = 0.4)

Fields

The type parameter F is the strategy the forcing builds into.

  • parameters — the keywords given, an omitted target held as nothing.

Forcing methods

This section documents the method that creates a strategy's evolving state, then the four methods a strategy may define, each doing nothing by default, in the order a run calls them: steady_linear_rate, once, when the generator is built; prepare_forcing!, once per step; add_forcing_source!, at every Runge–Kutta stage; and project_forcing!, after the step.

GBGHomogeneousTurbulence.Forcing.initial_forcing_state — Function
initial_forcing_state(forcing, field, domain)

Create a forcing strategy's initial state.

Arguments

  • forcing — the strategy.
  • field — the velocity or the scalar in spectral representation; its tensor order sets how many components the state carries.
  • domain — the FixedDomain.

Returns nothing for a strategy that evolves no state of its own: the default, and the case of every strategy but StochasticOU, which returns a StochasticOUState holding its random process.

A run calls this once per forced field and keeps the result as the modeled entry of its ResolvedFields, which prepare_forcing! advances in place every step. The strategy holds only parameters and scratch, so a checkpoint of the state resumes a forced run exactly.

GBGHomogeneousTurbulence.Forcing.steady_linear_rate — Function
steady_linear_rate(forcing, domain)

The per-mode rate $A(\boldsymbol{\kappa})$ of a strategy forcing whose forcing is linear in the field and constant in time, $f = A \cdot \texttt{field}$, on the FixedDomain domain; nothing for every other strategy, the default. The scheme folds the rate into the diffusive integrating factor $\mathcal{E}(\boldsymbol{\kappa})$ (see velocity_integrating_factor), so the forced modes advance at the net linear rate $A(\boldsymbol{\kappa}) - D\lvert\boldsymbol{\kappa}\rvert^{2}$, with $D$ the field's diffusivity.

The generator calls it once, when it is built. A rate that is a function of $\lvert\boldsymbol{\kappa}\rvert^{2}$ alone is returned as a radial kernel, evaluated per mode inside the integrating factor and stored nowhere; any other rate as a scalar field in spectral representation holding real values.

Steady, not merely linear, is the load-bearing word: a per-mode rate re-solved from the state each step must not be returned here. Freezing it would be the left-endpoint rectangle rule on $\int A\,\mathrm{d}t$, dropping the scheme to first order; such a forcing goes through add_forcing_source! instead. This function is handed no field, so a rate it returns is steady by construction.

GBGHomogeneousTurbulence.Forcing.prepare_forcing! — Function
prepare_forcing!(forcing, forcing_state, field, domain, dt) -> nothing

Advance the strategy forcing's evolving state by one step, before the Runge–Kutta stages begin. The state is mutated in place, so it holds its end-of-step value when this call returns; the default does nothing.

Everything the stages will need must be ready when this returns, since add_forcing_source! is handed no timestep of its own.

Arguments

  • forcing — the strategy whose state advances.
  • forcing_state — the state initial_forcing_state created once, advanced by this call on every step since. It is nothing for a strategy that evolves no state.
  • field — the start-of-step velocity or scalar, in spectral representation.
  • domain — the FixedDomain the run advances on.
  • dt — the step about to be taken.

GBGHomogeneousTurbulence.Forcing.add_forcing_source! — Function
add_forcing_source!(forcing, forcing_state, N̂, field, domain, diffusivity) -> N̂

Add the strategy forcing's source term to the assembled right-hand side N̂, at every Runge–Kutta stage. The default does nothing.

Two kinds of strategy add a source here. One measures the stage's own field and sets its amplitude from it — ConstantPower and VarianceController do, and this is the only route open to them, since a state-dependent rate frozen once per step would drop the scheme to first order. The other carries a source that does not read the field at all: StochasticOU's random process, already advanced for this step by prepare_forcing!, which this call only writes into N̂.

Arguments

  • forcing — the strategy adding the source.
  • forcing_state — its evolving state as prepare_forcing! left it this step, or nothing for a strategy without one. This call reads it and does not advance it.
  • N̂ — the assembled right-hand side, accumulated into.
  • field — this stage's own velocity $\hat{\boldsymbol{u}}$ or scalar $\hat{\varphi}$, in spectral representation, whichever the strategy drives.
  • domain — the FixedDomain the term is assembled on.
  • diffusivity — the diffusivity acting on the forced field: $\nu$ for the velocity, $\varkappa$ for the scalar.

Measuring the field costs one blocking device-to-host transfer at every stage, and that is the price of the order this route preserves. A single fused multi-weight reduction answers VarianceController's three weighted sums together, and ConstantPower reads its band the same fused way. A strategy that reads nothing pays nothing: StochasticOU makes no such transfer, and Linear, which takes the rate route instead, makes none either.

The source is accumulated, never assigned

Every stage adds into an N̂ the generator has already filled with the nonlinear term, so an implementation must add its contribution and must not overwrite the buffer.

Persistence

This section documents a strategy's HDF5 persistence: its defining parameters as one self-describing group, available once HDF5 is loaded.

GBGHomogeneousTurbulence.Forcing.write_forcing — Function
write_forcing(parent::HDF5.H5DataStore, name::AbstractString,
              forcing::AbstractForcing)

Write the forcing strategy forcing (an AbstractForcing) under parent as one self-describing HDF5 group — its defining parameters only; every derived object (a band kernel) is rebuilt from them on read. What a strategy evolves is not a parameter: the process of a StochasticOU lives in the run's state and is stored by write_state, so a reloaded strategy continues the same realization when the state is restored with it. A DeferredForcing is refused — resolve it on a domain first. Available once the HDF5 package is loaded; the caller owns the file.

Arguments

  • parent — the open HDF5 file or group to write under.
  • name — the created group's name.
  • forcing — the built strategy to record.

Returns the created group. Reload with read_forcing.
