Particles

GBGIsotropicTurbulence.Particles — Module
Particles

Lagrangian tracer tracking:

  • Tracers — the tracer set (positions and a selectable interpolation_scheme).
  • particle_positions, number_of_particles — the particle-state readouts (the trajectory velocities are read from the run's observables cache through particle_velocities — the same quantity the docs also call the Lagrangian velocity or the trajectory velocity — where the closing deposit leaves them).
  • AbstractParticleIntegrator, EndpointHeun — the trajectory time-integration schemes, and ParticleIntegratorBuffers the per-step storage each one needs.
  • record_particle_velocities! — store the flow velocity at the tracers' current positions, which is both the measured Lagrangian sample and the first velocity the next advance needs.
  • advect! — advance the trajectories one step under the chosen scheme.
  • interpolate_at_particles! — read a field along the trajectories; new_vector_point_values / new_scalar_point_values allocate its out buffers.
source

The tracer set

Tracer positions plus a selectable interpolation scheme, with the accessors that read a tracer set's state — its positions and its count. The set holds trajectory state only; a scheme's working storage lives apart.

GBGIsotropicTurbulence.Particles.Tracers — Type
Tracers(domain; number_of_particles, interpolation_scheme, rng = default_rng())
Tracers(domain; positions, interpolation_scheme)

(One method, shown as the two ways it is called — keywords do not dispatch.)

A set of Lagrangian tracers, built on domain's backend and element type.

Give exactly one of number_of_particles, which seeds that many tracers uniformly at random in the periodic box, or positions, an (M, 3) array of tracer positions to wrap (the columns being the $x, y, z$ components), converted to domain's backend and element type. Supplying both, or neither, raises an ArgumentError.

The interpolation_scheme is the GBGPeriodicFields scheme used to evaluate the velocity — and any sampled field — at the tracer positions. CatmullRom is the $C^1$ choice and the front door's default; it is a ready-made value rather than a type, so it is passed bare. LalescuSpline(n, m) and LagrangeSpline(n) offer higher smoothness or interpolation order at a wider stencil — useful for derivative-sensitive readouts such as acceleration statistics — with n (and, for LalescuSpline, m) the stencil and smoothness parameters.

Arguments

  • domain — the FixedDomain whose backend, element type and box the set is built on.
  • number_of_particles — seed this many tracers uniformly at random in the box.
  • positions — or wrap this (M, 3) array instead; give exactly one of the two.
  • interpolation_scheme — the scheme used to evaluate a field at the tracer positions.
  • rng — the random stream seeding the positions (used with number_of_particles, ignored with positions); defaults to Random.default_rng().

Examples

A run carries tracers when the front door is given a count; advance! then advances them with the fields and records the Lagrangian velocity each iteration, so both reads below are current between iterations:

sim = Simulation(grid_points_per_axis = 64, number_of_particles = 4096, scalar = true)
advance!(sim)

X = particle_positions(sim.tracers)         # the (M, 3) positions at this instant
v = particle_velocities(sim.cache)          # u(tₙ, X(tₙ)), the Lagrangian velocity — a checked read

out = new_scalar_point_values(sim.tracers)  # allocate once, then reuse every iteration
interpolate_at_particles!(out, scalar_physical(sim.cache), sim.tracers)

Building a set directly — to place tracers deliberately rather than at random, and to advance them by hand — takes the positions form, and then the scheme's per-step storage is yours to allocate:

tracers = Tracers(domain; positions = [0.1 0.2 0.3; 1.0 1.0 1.0], interpolation_scheme = CatmullRom)
buffers = allocate_buffers(EndpointHeun(), tracers)

record_particle_velocities!(tracers, u)     # u(tₙ) at the current positions — do this first
advect!(EndpointHeun(), tracers, u_end, domain, buffers, dt)

Read the particle state with particle_positions and number_of_particles, both of which read the tracer set directly. The velocities are the exception, and deliberately so: they are a deposited observable rather than tracer state, so they are read from the run's observables cache through particle_velocities, where the iteration's closing deposit leaves them.

The trajectory scheme's own working storage is not here: it lives in a ParticleIntegratorBuffers, whose docstring explains the split.

Fields

  • positions — the (M, 3) tracer positions (read with particle_positions).
  • position_points — a PointSet wrapping positions: the same coordinates in the form GBGPeriodicFields' interpolation takes, which is why both exist.
  • particle_velocities — the interpolated velocity at the positions the tracers occupy, at the instant they occupy them: the genuine Lagrangian sample. This array is the observables cache's particle-velocities slot, the same storage under two names, so it carries that slot's rules — read it through particle_velocities, which serves it only when current, and treat it as read-only, since the tracer advance writes here mid-iteration.
  • interpolation_scheme — the scheme used to evaluate a field at the tracer positions.

The trajectory scheme

How the positions are advanced over one step — the Lagrangian counterpart of the field schemes. EndpointHeun reaches second order with a second interpolation per step; AdamsBashforth reaches further by reusing the Lagrangian samples already deposited, at no extra interpolation. Each scheme's storage is allocated by allocate_buffers, which a run calls for you.

GBGIsotropicTurbulence.Particles.AbstractParticleIntegrator — Type
AbstractParticleIntegrator

The supertype of the trajectory time-integration schemes — how the tracer positions are advanced over one step, the Lagrangian counterpart of the field side's AbstractIntegrator. A scheme is a value (EndpointHeun()), passed to advect! and to allocate_buffers, which builds exactly the working storage that scheme needs.

Two members today: EndpointHeun, a one-step method that buys second order with a second interpolation, and AdamsBashforth, a multistep method that buys more by reusing the Lagrangian samples the run already deposits. Which trade a run wants is a fitness question — one interpolation per step against one stored array per extra order.

source
GBGIsotropicTurbulence.Particles.EndpointHeun — Type
EndpointHeun()

Second-order Heun-in-time on the velocity at the two ends of the step — the trajectory scheme a run uses by default. It advances the positions with the start-of-step Lagrangian velocity that record_particle_velocities! stored and the end-of-step velocity field the solver has just produced, so it needs nothing from inside the field scheme's stages.

It needs one set of predicted positions and the velocity interpolated there (ParticleIntegratorBuffers); the formula is given with advect!.

Pair it with the default interpolant unless the grid is coarse

Under the advective-CFL loop $\Delta t \propto \Delta x$, so this scheme's error falls as $\Delta x^{2}$ while a degree-$d$ interpolant's trajectory floor falls as $\Delta x^{d+1}$. For the default CatmullRom (degree 2) the floor therefore falls faster than the time error, and the two cross over: measured on a band-limited field, interpolation dominates at $N = 16{-}32$ and the time error dominates from $N \approx 64$ on (at $N = 128$, floor $1\times10^{-5}$ against time error $6\times10^{-5}$). So at production resolutions CatmullRom is not what limits a Heun trajectory and a wider stencil buys nothing; at coarse resolution, or with $\Delta t$ cut well below the CFL value, LalescuSpline(3, 1) — same $C^1$, degree 3 — moves the floor down by more than an order of magnitude. What governs this in a run is how well the grid resolves the dissipation scale, so read $N$ here as a stand-in for $\kappa_{\max}\eta$.

GBGIsotropicTurbulence.Particles.AdamsBashforth — Type
AdamsBashforth(; order = 4)

Variable-step Adams–Bashforth trajectory integration — the scheme TurTLE uses for its tracers, at its default order — buying accuracy in time at no extra field evaluation and no extra interpolation per step.

Use it in place of EndpointHeun when trajectory accuracy in time limits a measurement. Heun buys its second order by interpolating a second time, at predicted positions; Adams–Bashforth instead reuses the Lagrangian samples the run has already deposited at earlier instants. The trade is one stored array per extra order against one interpolation per step.

The steps are not assumed uniform: the advective-CFL loop changes $\Delta t$ every iteration, which classical fixed-step coefficients would silently get wrong, so the weights are recomputed each step from the actual step history. That is $\mathcal{O}(\texttt{order}^2)$ host arithmetic per step, independent of the tracer count.

A multistep method has no history at $t_0$, so the first order - 1 steps are taken with EndpointHeun and the scheme then switches over; the same restart happens if the tracers are reseeded. Those second-order starting steps leave a fixed error behind, so over a fixed window order = 4 converges at about third order rather than fourth — on a smooth test problem, $3.0$ against $2.0$ for the two-step method, with an error some fifty times smaller at equal step count. A higher-order start would need the velocity between the step endpoints, which the solver does not produce.

Arguments

  • order = 4 — how many past samples are used. 1 is forward Euler, 2 the two-step method, 4 TurTLE's default. Capped at 8, which is where the four-point Gauss–Legendre rule that integrates the interpolation weights stops being exact; the cap is far above any useful order, since an Adams–Bashforth stability region shrinks with each step added.
The interpolant sets a floor no timestep can cross

Interpolating the velocity perturbs the field the tracers follow, and that perturbation does not shrink with $\Delta t$: for a perturbation $\epsilon$ and Lipschitz constant $L$, Grönwall bounds the trajectory error by $\epsilon(\mathrm{e}^{LT} - 1)/L$ however the time integration is done. Refining the step, or raising order, pays only until the time error reaches that floor.

The floor is set by the interpolant's polynomial reproduction degree, not its smoothness class — measured here, raising the degree at fixed $C^1$ lowered it fifty-fold, while varying the smoothness at fixed degree left the time convergence unchanged. Raise the degree when the floor is what limits you; smoothness buys something different, namely readouts that differentiate the interpolant, such as acceleration (Lalescu, Teaca & Carati 2010, doi:10.1016/j.jcp.2010.04.006).

Reference: Adams–Bashforth applied to Lagrangian tracers as in TurTLE (Lalescu et al. 2022, TurTLE: a fast and scalable code for turbulence, Comput. Phys. Commun. 278, 108406, doi:10.1016/j.cpc.2022.108406), whose default is the four-step method.

GBGIsotropicTurbulence.Particles.ParticleIntegratorBuffers — Type
ParticleIntegratorBuffers

The per-step storage a trajectory scheme computes in, sized to a tracer set and allocated once, so advancing the tracers allocates nothing. Build it with allocate_buffers(scheme, tracers), which allocates exactly what scheme needs and nothing more; a run builds it for you.

This storage belongs to the scheme, not to the trajectory: a different scheme wants a different set — a multistep scheme wants a velocity history and no predicted positions at all — which is why it lives here rather than in Tracers.

Fields

  • predictor — the (M, 3) predicted positions, which no tracer ever occupies.
  • predictor_points — a PointSet wrapping predictor.
  • velocity_predictor — the velocity interpolated at the predicted positions (the particle-side counterpart of the field schemes' velocity_predictor_spectral). It is reachable like any field of this type, but it is a scheme intermediate rather than a sample of the flow at any instant, so nothing in the package offers it as one: read particle_velocities for the Lagrangian sample.
source
GBGIsotropicTurbulence.Particles.MultistepBuffers — Type
MultistepBuffers

The per-scheme registers of an AdamsBashforth trajectory integrator: the startup scheme's registers, the host scratch its weight solve works in, and the cache it reads its past Lagrangian samples from.

Build it with allocate_buffers(scheme, tracers, cache); a run builds it for you.

The past samples themselves are not held here. They are deposited observables — measurements of the velocity along the trajectory — so they live in the ObservablesCache beside the current sample they extend, which is what lets particles_modified! invalidate the whole history when the tracers are repositioned.

Fields

  • cache — the ObservablesCache holding the sample history this scheme integrates over.
  • startup — the ParticleIntegratorBuffers the bootstrap EndpointHeun steps use.
  • weights, nodes — the order-element host scratch the per-step weight solve works in.

The tracking loop

The steps of Lagrangian tracking: record the flow velocity where each tracer currently sits, advance the tracers once the fields have moved, then read any physical field along the trajectories for the Lagrangian statistics. Recording and pushing are two verbs because EndpointHeun needs the velocity at both ends of the step: the run records the sample at the iteration's end, off the just-deposited velocity, and the next iteration's advect! reads it back as the first half of its pair.

GBGIsotropicTurbulence.Particles.record_particle_velocities! — Function
record_particle_velocities!(tracers, u) -> tracers

Store the Lagrangian velocity $\boldsymbol{u}(t_n, \boldsymbol{X}(t_n))$ — the flow velocity seen by each tracer where it currently sits — by interpolating the velocity field u (physical representation) onto the positions of the tracer set tracers, with the set's interpolation scheme.

The values go into the tracer set's own particle_velocities storage, which is also the observables cache's particle-velocities slot. This call is that slot's only producer of values, but it writes values only: the slot stays stale, and reads of it throw, until deposit_sample! records them as current. Interpolate here, then mark current there — a run does both at the end of each iteration, on the just-deposited velocity at the just-advanced positions, and reading particle_velocities after only the first throws.

The stored values serve twice: they are the genuine Lagrangian velocity a caller accumulates, and they are the start-of-step velocity $\boldsymbol{v}_1$ the next advect! needs — which is why an EndpointHeun advance never interpolates at $t_n$ itself. Storing them costs $M\times3$ values for $M$ tracers, where keeping the velocity field would cost $N^{3} \times 3$.

GBGIsotropicTurbulence.Particles.advect! — Function
advect!(scheme, tracers, velocity_end, domain, buffers, dt) -> tracers

Advance the positions of the tracer set tracers by one step of size dt (written $\Delta t$ below), in place, under the trajectory scheme scheme (an AbstractParticleIntegrator), using its working storage buffers (a ParticleIntegratorBuffers built for that scheme). The domain (a FixedDomain) supplies the box side the positions are wrapped into.

Under EndpointHeun, the scheme is Heun-in-time on the velocity at the two ends of the step — the start-of-step values that record_particle_velocities! stored, and velocity_end, the end-of-step velocity field $\boldsymbol{u}(t_{n+1})$ in physical representation:

\[\begin{aligned} \boldsymbol{v}_1 &= \boldsymbol{u}(t_n, \boldsymbol{X}), & \boldsymbol{X}^{*} &= \boldsymbol{X} + \Delta t \boldsymbol{v}_1, \\ \boldsymbol{v}_2 &= \boldsymbol{u}(t_{n+1}, \boldsymbol{X}^{*}), & \boldsymbol{X} &\leftarrow \boldsymbol{X} + \tfrac{\Delta t}{2}(\boldsymbol{v}_1 + \boldsymbol{v}_2), \end{aligned}\]

with positions wrapped into $[0, L)$. This is second-order accurate in time — advecting on the frozen start-of-step velocity alone would be first order.

The start-of-step velocity is read, never recomputed

$\boldsymbol{v}_1$ is read from the tracer set, not recomputed here: it must hold $\boldsymbol{u}(t_n, \boldsymbol{X}(t_n))$, recorded by record_particle_velocities! at the previous iteration's end. In a run the observables cache records that sample at its epoch and the run layer reads it checked before each advance; a hand-run loop must call record_particle_velocities! itself between advances.

GBGIsotropicTurbulence.Particles.restart! — Function
restart!(scheme, buffers) -> buffers

Discard whatever history buffers holds, so the next advect! starts the scheme from scratch.

Call it whenever the tracer positions are changed from outside the iteration — a reseed, a hand-written correction, any direct write to the tracer storage. A one-step scheme carries no history and this does nothing; a multistep scheme carries Lagrangian samples taken along the trajectory that has just been abandoned, and integrating over those would blend the old path with the new one. The Simulation form of particles_modified! calls this for you, after announcing the reposition to the observables cache. Its bare-cache form clears the sample history the cache itself holds, but cannot dispatch here — so a hand-run loop that announces to the cache alone must call this as well, and a scheme carrying registers beyond that history is reached only this way.

Returns buffers.

source
GBGIsotropicTurbulence.Particles.history_depth — Function
history_depth(scheme) -> Int

How many Lagrangian samples scheme must be able to look back over, counting the current one.

A run reads this to size the sample history its ObservablesCache carries. A one-step scheme answers 1 and needs no history stored; an order-step method answers order.

GBGIsotropicTurbulence.Particles.interpolate_at_particles! — Function
interpolate_at_particles!(out, field, tracers) -> out

Sample the physical field at the current tracer positions into the point-value buffer out (a VectorPointValues for the velocity, a ScalarPointValues for the scalar $\varphi$), using the interpolation scheme of the tracer set tracers. This is how a field is gathered along the trajectories; what is then accumulated over those values is the caller's own analysis.

Wiring tracers into a run

Pass number_of_particles to the front door and the run carries a tracer set: advance! pushes it every iteration and records the Lagrangian sample, so the reads below are always current between iterations.

sim = Simulation(grid_points_per_axis = 64, number_of_particles = 4096)
warmup!(sim)
advance!(sim)

particle_positions(sim.tracers)              # (M, 3) positions at the current instant
particle_velocities(sim.cache)               # u(tₙ, X(tₙ)) — the Lagrangian sample, a checked read
out = new_vector_point_values(sim.tracers)   # allocate once, then reuse
interpolate_at_particles!(out, velocity_physical(sim.cache), sim.tracers)
