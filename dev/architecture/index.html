Architecture

Written by AI, not regularly reviewed

This page is written by AI and is not reviewed regularly by a human.

This is the design document for GBGHomogeneousTurbulence — what the package is, how it is organized, and why it is shaped the way it is. It is the spec: read it before any structural change, and do not re-litigate a recorded decision (§11) without the user. CLAUDE.md is the terse working copy and defers here; the rendered symbol glossary is docs/src/notation.md.

The document is self-contained — every symbol, mathematical or code, is introduced in plain language at first use — and reads top to bottom. Mathematics follows the glossary's notation: the wavenumber vector is $\boldsymbol{\kappa}$ with magnitude $\kappa$; the turbulent kinetic energy is $k$; the scalar diffusivity is $\varkappa$; the integrating factor is $\mathcal{E}$. Pope (2000) is a standard reference for turbulence notation (§References).

1. Identity

GBGHomogeneousTurbulence is a small, focused pseudospectral direct numerical simulation (DNS) of homogeneous isotropic turbulence: one incompressible velocity field $\boldsymbol{u}$ and one passive scalar $\varphi$ on a triple-periodic box, advanced by interchangeable integrating-factor time-stepping, with Lagrangian particle probes and field sampling along their trajectories. It is a library of composable pieces with a thin ergonomic run layer on top, built as a consumer of GBGPeriodicFields (the field and spectral machinery) and GBGStreamingStatistics (the statistics — the division is settled and the bridge to it is deferred, §4.9).

It is not a general PDE or CFD framework, and not multi-physics: the physics is a thin, fixed core — Navier–Stokes plus one passive scalar, no chemistry, phases, or processes. It is not dimensional — control is by Reynolds and Schmidt number, never units. It is not a field library (that is GBGPeriodicFields) or a statistics library (that is GBGStreamingStatistics), and it builds no speculative extension points — no generality ahead of a concrete need (§9).

The package inverts the richness of its sibling consumer GBGCloudPhysics: where Cloud carries a rich constitutive physics over a thin numerical core, GBGHomogeneousTurbulence carries a thin fixed physics over rich, interchangeable numerics and statistics. That inversion is the single fact that explains most of what follows.

The first scientific goal is to measure the kinetic energy in box units (built from the box side $L$ and the dissipation rate $\varepsilon$) $\tilde{k} = k/(\varepsilon L)^{2/3}$ as a law $\tilde{k}(\text{forcing}, \mathrm{Re}, \text{band})$, integrate it so that a run's derived viscosity is calibrated for the forcing it actually uses, and publish it (decisions 94 and 101). This $\tilde{k}$ is the constant by which the run layer turns a requested resolution into a viscosity, and the package's first sweep showed it is not universal. Until the law exists, the run layer predicts with provisional values per forcing band (0.72 for shells 1–2, 0.56 for 1–4, 0.47 for every mode), flat in the Reynolds number.

2. Running a simulation

The primary measure of this library's quality is how easily one sets up and runs a case — including warm-up to a statistically stationary state before any measurement. The headline interface is therefore a thin run layer that assembles the machinery with sensible defaults and owns the time loop:

using GBGHomogeneousTurbulence

# Assemble a forced case. Everything the run needs — the domain, buffers, physics,
# scheme, state, and initial condition — is built with defaults from a few numbers.
sim = Simulation(grid_points_per_axis = 128, viscosity = 1e-2;
                 velocity_forcing = ConstantPower(injection_rate = 0.1),
                 scalar = PassiveScalar(schmidt = 1.0))

# Spin past the transient: advance until the running dissipation ε(t) stops
# drifting. The kinetic energy k(t) is not the test: under a fixed-injection
# forcing like this one it overshoots, then wanders.
warmup!(sim)

# Advance until the stopping criterion returns false. It is called once at the
# start and after every iteration; it records what it wants and its return
# decides continuation — stopping is the caller's decision.
energies = Float64[]
t_end = current_time(sim) + 20.0
run!(sim) do s
    push!(energies, kinetic_energy(s.state.velocity_spectral))
    current_time(s) < t_end
end

The run layer holds the pieces of §4 in one Simulation value. Each iteration it chooses a stable timestep from the advective-CFL condition over the cached maximum speed (§4.5) and serves the deposited observables from the deposit-driven ObservablesCache (§4.1). Its loop calls the stopping criterion once at the seeded $t_0$ and after every iteration — $n$ iterations, $n+1$ calls — which reads the run and decides whether it continues (§11 decision 43). Spin-up is the packaged StationarityCriterion, warmup! its one-line sugar: it advances until the flow is statistically stationary, watching the running dissipation $\varepsilon(t)$ — a small-scale signal that settles late — rather than the kinetic energy a constant-energy forcing clamps flat, with the velocity-derivative skewness $S(t)$ an opt-in second gate (gate_skewness, off by default since decision 78); §4.7 gives the exact stopping test. A forced flow must reach statistical stationarity before a structure function or a PDF taken over it means anything.

The composable pieces stay fully exposed: a study that needs to run the loop by hand, swap a stage, or interleave a bespoke measurement drops straight to §4. The run layer is a convenience over that machinery, never a wall in front of it.

Status. The run layer is implemented (module SimulationRun) and covered by tests; the example above runs as written — a forcing can be named before its domain exists (ConstantPower(injection_rate = 0.1), a DeferredForcing) and warmup! detects stationarity. The API may still evolve, since setup ergonomics is the package's primary quality target.

3. The organizing frame

A run is fixed by two independent things: what continuous problem you pose, and how you realize it numerically. Beneath both lies a single organizing idea.

The foundation — one dynamics under a ladder of projections

The architecture is founded on the Mori–Zwanzig decomposition. One dynamics, seen under a ladder of projections, resolves into the four roles every rung shares — State, Generator, Observables, Propagator — and the modules are those roles. The decomposition can bear this weight because it is exact: projecting the full dynamics onto a coarser description is not an approximation but an identity, one that leaves behind an exact memory and an exact noise. What is investigated, never assumed is the closure — the model of that memory. So founding the architecture on Mori–Zwanzig and refusing to assume the physics are one commitment, not two: the framework is exact, and the approximation it demands is precisely the research question.

The four roles are level-agnostic — a DNS, a large-eddy model, and a moment closure all carry them, differing only in which state each holds and how much memory its generator must model:

  • the State — the field the dynamics acts on (§4.1);
  • the Generator — the right-hand side that evolves it, itself split into a reversible and an irreversible part (§4.2);
  • the Observables — the measured functions of the state (§4.3);
  • the Propagator — the map that advances the state through time, realized by a choice of integrating-factor scheme (§4.5).

Today only the finest rung, DNS, is built. The roles are named and carved so the coarser rungs slot in without re-carving (§7), but no generality is built ahead of them.

Specification and realization

On this foundation, a run is fixed by a specification — the continuous problem — and a realization — the numerics. The specification has two parts:

  • The System: the flow scenario — forced homogeneous isotropic turbulence, freely decaying turbulence, and — each deferred, §7 — uniform-mean-gradient scalar mixing (its source term is not yet built) and homogeneous shear (its frame is not). A System is a choice of forcing, initial condition, and the dimensionless parameters $\mathrm{Re}$ and $\mathrm{Sc}$.
  • The Model: the level of description — a rung on the ladder of projections. DNS resolves every active scale; a large-eddy Model resolves the large scales and models the rest; a filtered-density-function or moment Model carries statistics rather than fields. Descending the ladder applies a coarser projection, and the memory it leaves is what the Model's closure must supply.

The realization is the Method — the numerics — in two layers the package keeps distinct:

  • A Model-fibered family — the choices that only make sense for a given Model: the time-stepping scheme and its dealiasing for a field Model (§4.5), or the particle pushers and mixing model a statistical Model would need. The Model sets these.
  • Model-agnostic axes — precision, memory footprint, and compute backend (§6) — which cut across every Model uniformly.

Naming these apart is why the frame is specification × realization rather than three co-equal axes: the Method is fibered over the Model, not independent of it.

The comparison machine

Two research disciplines live on these two kinds of variation:

  • Method-independence. Vary the realization, hold the specification fixed, and the answer must not change beyond discretization error. Two schemes, two precisions, or two grid sizes for the same DNS must agree; agreement is the correctness signal, and the cheapest realization that still agrees is a finding, not merely a default.
  • Statistical commutation. Descend the Model ladder, hold the System fixed, and the coarse Model must reproduce the fine Model's statistics. Filtered DNS against LES of the same flow is the test — a match in distribution, never pathwise (§8), because the coarse state cannot determine its own tendency, and that missing tendency is exactly the Mori–Zwanzig memory. This is the closure question made operational.

Both disciplines are the same comparison machine — run a configuration against a reference and check chosen physical functionals (spectra, fluxes, conserved quantities, a target statistic) within tolerance — pointed at different axes. Those functionals are exactly the Observables of §4.3. The machine is a discipline the caller runs, not a component the package ships: the package provides the two sides — the measured observables and the reference laws — and no public comparer (its own test suite practices the comparison internally).

4. Modules

Each concern is its own module, included in dependency order by the umbrella src/GBGHomogeneousTurbulence.jl. The four Mori–Zwanzig roles carry their role names — State, Generator, Observables, Propagator; the System's forcing, the discretized frame, the Lagrangian instruments, the run layer, and the reference laws are named by their job. The rule is that a role recurring at every rung of the ladder wears its role name, while a concrete mechanism wears its job — so the load-bearing structure is legible at a glance, and no piece of plain machinery is dressed in theory it does not carry.

4.1 State and SimulationDomain — the field and the frame it lives on

Two modules separate what evolves from the frame it evolves on.

  • SimulationDomain provides the discretized periodic box the run lives on — the reusable, read-only frame. Its concrete type is the FixedDomain, the fixed, unsheared cube. It bundles the grid, the real–Fourier layout, and the real-to-complex transform plans — one rank-blind pair shared by every field, the velocity, the scalar, and the rank-2 strain tensor of the skewness diagnostic alike (decision 81), planned under the caller's fft_flags / fft_timelimit request, forwarded verbatim to the field library (a CPU lever — FFTW's default heuristic mis-plans single-precision transforms; the GPU libraries take no flag). On top of those sit the per-mode symbols: the spectral multipliers; $\lvert\boldsymbol{\kappa}\rvert^2$ as a lazy radial kernel, never materialized (in spectral space $-\nabla^{2}$ is multiplication by it, evaluated per mode — decision 38); the constant-1 unit_kernel in the same lazy form, so a plain variance can join a fused multi-weight reduction (decision 63); and the dealias kernel of the run's chosen strategy (the sharp $2/3$ rule by default), likewise a compressed symbol. The name marks what can vary: a FixedDomain has time-independent, separable wavenumbers, unlike the deferred sheared frame (ShearedDomain, §7). Precision and backend enter here and flow everywhere from here: element_type fixes the real element type (Float32 or Float64) and array_family its arrays (Array, CuArray, ROCArray), and every buffer is allocated similar to this frame, so a run is CPU/GPU-agnostic and single- or double-precision by construction.

  • State owns the DNS realization of the Mori–Zwanzig State role. ResolvedFields is the record of the evolving fields in spectral representation — the velocity $\hat{\boldsymbol{u}}$ and, when the run carries one, the scalar $\hat\varphi$ — together with the modeled slot holding any forcing's evolving state (§8), and the single source of truth: the physical velocity, vorticity, and scalar are functions of it, never independent state. No operation hangs on it; the generator advances it and the observables read it, both as external functions of $(\hat{\boldsymbol{u}}, \hat\varphi)$ — the reification the Mori–Zwanzig lens demands, kept a bare carrier so the operations acting on it, not the record itself, carry the design (§11 decision 26).

    The chart map — the recovery of the physical representations — is not a package verb. The velocity and scalar are recovered by the source-preserving four-argument form of GBGPeriodicFields' to_physical!, whose extra argument is a scratch field the transform consumes in the state's place, at the sites that consume them; the derived vorticity comes from Observables.vorticity_physical! (decision 47).

    The recovered values land in the ObservablesCache — its own module, Cache, included after Observables. That is the storage each iteration fills at its end with its observables: the physical velocity, vorticity and scalar, the maximum speed, and, when tracers ride the run, the velocity at the particles $\boldsymbol{u}(t_n, \boldsymbol{X}(t_n))$ (tracer positions $\boldsymbol{X}$, current time $t_n$). It fills them under the no-recompute rule (docs/src/observables_cache.md is the design page; §11 decision 40).

    A slot IS its producer's register: the step takes the chart arrays as its substage recovery registers mid-iteration (their epochs go to scratch, so a mid-iteration read throws instead of serving a stage intermediate), and the closing deposit! re-fills them at the new epoch from the state the step just produced. An accessor (velocity_physical, vorticity_physical, scalar_physical, the cached max_speed) serves the deposited value or throws; no read ever causes a computation.

    Freshness is tracked by one epoch counter per dynamical factor of the run — fields, particles. A completed step! advances the fields epoch. A change to the state's spectral representation made outside the iteration is the one freshness event the cache cannot detect itself, so it is declared through fields_modified! — or, for such a change to the tracer positions, through the particle-side twin particles_modified! — and followed by a deposit! before the run advances again (§11 decision 30). The State module's initial conditions seed the state: random_solenoidal_velocity_spectral! fills a divergence-free velocity with a large-scale spectral envelope, rescaled to a target $k$, and random_scalar_spectral! fills a mean-zero scalar to a target variance. The per-step scratch is not state: the scheme's registers live with the scheme (IntegratorBuffers in Propagator, §4.5) and the assembly scratch with the generator (ResolvedGenerator, §4.2). Each is preallocated, so a step allocates no field-sized memory (§9, invariant 4), and sized to the run — no scalar buffers when the run carries no scalar; GPU memory is tight. A Simulation composes the ResolvedFields and its ObservablesCache, and the time loop advances the state in place — each iteration a step! closed by the closing deposit!. Every concrete type of the package — the frame, the state, the cache, the forcings, the generator and its scratch, the register sets, the tracers and their scheme, the run, the stationarity records — carries a display in the field library's convention: one self-delimiting line carrying what the package refuses on, a REPL form where that line abbreviates, nothing reading an element (decision 87; the derived gate is test/display.jl).

4.2 Generator — the evolution, split reversible and irreversible

Generator realizes the Mori–Zwanzig generator: the right-hand side the propagator advances. Its physical inputs are bundled in FlowConditions — the viscosity $\nu$, the Schmidt number $\mathrm{Sc}$ (scalar diffusivity $\varkappa = \nu/\mathrm{Sc}$), and the two forcings; $\nu$ and $\mathrm{Sc}$ set the diffusion, the forcings the source, and folding this bundle into Generator is what adds the Generator → Forcing dependency. It carries a metriplectic seam — a reversible part that conserves energy and an irreversible part that dissipates it (§8) — and the numerical split is built to honor it. The incompressible momentum equation is advanced in rotational (Lamb-vector) form: writing the convective term through the identity $(\boldsymbol{u}\cdot\nabla)\boldsymbol{u} = \nabla(\tfrac{1}{2}\lvert\boldsymbol{u}\rvert^2) + \boldsymbol{\omega}\times\boldsymbol{u}$ (with vorticity $\boldsymbol{\omega} = \nabla\times\boldsymbol{u}$ and the Lamb vector $\boldsymbol{\omega}\times\boldsymbol{u}$, the literature's sign, decision 93) and letting the Leray–Helmholtz projection $\mathbb{P}$ onto divergence-free fields absorb the pressure and the kinetic-energy gradient, the equation with forcing $\boldsymbol{f}$ becomes

\[\partial_t\boldsymbol{u} = -\mathbb{P} (\boldsymbol{\omega}\times\boldsymbol{u}) + \nu\nabla^{2}\boldsymbol{u} + \boldsymbol{f}.\]

Its three terms are the seam made explicit, and the time-stepping treats each according to its nature:

  • The reversible term. The recoveries — the source-preserving four-argument to_physical! and the vorticity observable vorticity_physical! (decision 47) — produce the physical velocity and vorticity from $\hat{\boldsymbol{u}}$; velocity_rhs! then assembles $-\mathbb{P} (\boldsymbol{\omega}\times\boldsymbol{u})$, dealiased by the $2/3$ rule to remove the aliasing of the quadratic product (the pseudospectral method; Orszag & Patterson 1972, the $2/3$ rule Orszag 1971). Rotational form is the cheap way to compute the advection spectrally, and under a sharp mask the truncation is exactly Galerkin, so the discrete advection conserves kinetic energy (HouLi, which only damps, is the deliberately non-conservative strategy), and incompressible Euler is genuinely Hamiltonian — so this term is the flow's reversible, energy-conserving generator, stepped explicitly.
  • The irreversible term. The diffusion $\nu\nabla^{2}\boldsymbol{u}$ is the flow's irreversible, net-dissipative generator. Being diagonal in Fourier, it is integrated exactly through the flow map $\mathcal{E}(\boldsymbol{\kappa}) = \exp\bigl((A(\boldsymbol{\kappa}) - D\lvert\boldsymbol{\kappa}\rvert^2) \delta t\bigr)$ — the exact propagator of the linear part over an interval $\delta t$ (a Runge–Kutta stage substep, the fraction $d_i\Delta t$ of the step, or the whole step $\Delta t$), with diffusivity $D = \nu$ for the velocity and $D = \varkappa = \nu/\mathrm{Sc}$ for the scalar, and $A(\boldsymbol{\kappa})$ an optional linear forcing rate (the source, below). $\mathcal{E}$ is never materialized (decision 39): the factor pair velocity_integrating_factor / scalar_integrating_factor supplies its parameters — the coefficient on $\lvert\boldsymbol{\kappa}\rvert^2$ and any steady forcing rate, fixed when the generator is built — and the backend's fused exponential convolution evaluates $\mathcal{E}$ per mode as it applies it, advancing the diffusion with no stability restriction and no kernel field built or stored. $\mathcal{E}$ is a propagator, a flow map over a step, not a generator; keeping the two apart is exactly the Generator/Propagator distinction of §4.5.
  • The source. $\boldsymbol{f}$ is the forcing, an external drive that is neither seam half (§4.4). When a forcing is linear in the field ($\boldsymbol{f} = A \boldsymbol{u}$) with a steady rate, that rate $A(\boldsymbol{\kappa})$ is diagonal and linear like the diffusion, so it folds into the same exponential $\mathcal{E}$ for exactness — and there it injects energy, $\mathcal{E} > 1$ wherever $A > D\lvert\boldsymbol{\kappa}\rvert^2$. So $\mathcal{E}$ cross-cuts the seam: it carries the irreversible diffusion and, when the drive is linear and steady, the source. The seam is a decomposition of the right-hand side, not of $\mathcal{E}$.

The passive scalar rides the same generator: the source-preserving four-argument to_physical! recovers the physical $\varphi$ from $\hat\varphi$ at each stage, and scalar_rhs! assembles the advection in conservative form $-\nabla\cdot(\boldsymbol{u}\varphi)$ (equal to $-\boldsymbol{u}\cdot\nabla\varphi$ since $\nabla\cdot\boldsymbol{u} = 0$); the conservative form conserves the scalar mean exactly under the $2/3$ rule.

The metriplectic reading is a lens, not a literal thermodynamics: incompressible isothermal flow carries no genuine entropy — the dissipated kinetic energy simply leaves the model as untracked heat — so the load-bearing content is the reversible/irreversible split of the right-hand side and the constraint it puts on any closure: net dissipation lives in the diffusion term alone, so a subgrid model may only remove energy through that half (§8).

The generator is reified: ResolvedGenerator bundles the FlowConditions with the assembly scratch its evaluations write through (the quadratic products' spectral image, the PhaseShift displaced-evaluation buffers, any steady forcing rate — in physical representation each quadratic product forms in place over an operand's own register, §11 decision 41), behind a six-verb protocol — prepare! opens the step (advances each forcing's evolving state), velocity_rhs! / scalar_rhs! evaluate each field's explicit right-hand side at a stage state (dealiased nonlinear term plus additive forcing source), velocity_integrating_factor / scalar_integrating_factor supply each field's exact linear subflow, and finalize! closes the step (the post-step forcing projections). The required core is velocity_rhs! and velocity_integrating_factor; prepare! and finalize! always run, and do nothing observable only when the configured forcing leaves prepare_forcing! and project_forcing! at their AbstractForcing defaults. A scheme consumes the physics only through this protocol, so it can never assemble the right-hand side from a mismatched intermediate — the class of the stage-ordering bug that motivated the reification (§11 decisions 29, 31).

4.3 Observables — the measured functions of the state

Observables realizes the Mori–Zwanzig observables: the functions of the state that are measured. Each states the physical quantity first, then the reduction that computes it:

  • $\texttt{kinetic\_energy} \equiv k = \tfrac{1}{2}\langle\lvert\boldsymbol{u}\rvert^2\rangle$ and $\texttt{dissipation} \equiv \varepsilon = \nu\langle\lvert\boldsymbol{\omega}\rvert^2\rangle$;
  • $\texttt{scalar\_variance} \equiv \langle\varphi^2\rangle$ and $\texttt{scalar\_dissipation} \equiv \varepsilon_\varphi = 2\varkappa\langle\lvert\nabla\varphi\rvert^2\rangle$;
  • max_speed, which sets the advective-CFL (one generic shared with Cache, where the cached read lives — the reduction is homed here, decision 46);
  • $\texttt{vorticity\_physical!} \equiv \boldsymbol{\omega} = \nabla\times\boldsymbol{u}$, the field-valued observable — the vorticity recovered in physical representation, whose cached read is Cache.vorticity_physical (decision 47);
  • derivative_skewness, the classical marker $S \approx -0.5$ of developed turbulence (an empirical, weakly Reynolds-number-dependent value — K41 implies a constant skewness but fixes no number), computed coordinate-free as the normalized third invariant of the strain rate $\boldsymbol{S}$, $3C_S\langle\det\boldsymbol{S}\rangle/\langle\boldsymbol{S}:\boldsymbol{S}\rangle^{3/2}$ with the exact isotropy constant $C_S = \tfrac{4}{7}\sqrt{15/2}$ (Betchov 1956; reproduces the classical longitudinal skewness);
  • $\texttt{energy\_spectrum} \equiv E(\kappa)$, the halved GBGPeriodicFields radial spectrum over the shell width — the density, the same object a model law gives — and integral_length derived from it;
  • kinetic_energy_and_dissipation_below_scale, the kinetic energy $k(l)$ and dissipation $\varepsilon(l)$ held in scales below each box side $l$ the grid offers — what a box of side $l$ measures once its own mean velocity (or mean strain rate) is removed, averaged over its positions — as the weighted reductions $\tfrac{1}{2}\sum(1 - W_l^2)\lvert\hat{\boldsymbol{u}}\rvert^2$ and $\nu\sum\lvert\boldsymbol{\kappa}\rvert^2(1 - W_l^2)\lvert\hat{\boldsymbol{u}}\rvert^2$ over GBGPeriodicFields' top-hat window (decision 96).

These are not incidental: they are the fitness functionals the comparison machine of §3 evaluates, and the stationarity signals warmup! watches. They are also the measured half of a comparison against the reference laws (§4.8).

4.4 Forcing — the source

Forcing is the System's energy-injection strategy — the source term $\boldsymbol{f}$ of §4.2, and the one deliberately designed-in extension point. AbstractForcing is the supertype; a forcing enters the step through a small interface of four methods, plus initial_forcing_state, starting the state the first advances; each defaults to doing nothing:

  • prepare_forcing! — advance the forcing's evolving state once per step (a stochastic process), a state initial_forcing_state starts and the run's ResolvedFields keeps as it advances;
  • steady_linear_rate — for a forcing linear in the field ($\boldsymbol{f} = A \boldsymbol{u}$) and steady in time: return the rate $A(\boldsymbol{\kappa})$, folded into the integrating factor; handed no field, it is steady by construction;
  • add_forcing_source! — add an additive source at each Runge–Kutta stage;
  • project_forcing! — apply a post-step projection or rescale.

A step calls the four in a fixed order — steady_linear_rate once, when the generator is built; then per step prepare_forcing! before the stages, add_forcing_source! at every stage, project_forcing! after the completed step. A forcing term divides as the rest of the equation does: its steady linear part joins the viscous term in $\mathcal{E}$ and is integrated exactly, and the remainder joins the explicit right-hand side, evaluated at every stage. A strategy owns whatever scratch its methods need; none receives the scheme's buffers (§11 decision 32). What a strategy evolves is not scratch: it lives in the modeled slot of ResolvedFields, so that one record is the whole evolving state of the run (§8's open-systems reading; §11 decisions 23 and 90).

Which of the four a strategy defines is not an implementation detail: it decides whether the strategy preserves the scheme's order in time. A rate folded into $\mathcal{E}$ is integrated exactly, but only a steady rate can be — freezing a state-dependent one at the step's start is the left-endpoint rectangle rule on $\int A\,\mathrm dt$, which is first-order however good the scheme is, and a post-step projection is Lie–Trotter splitting, first-order by construction. So a state-dependent forcing belongs in the source, where the scheme's own stages integrate it. Measured on the third-order IFLowStorageRK3: every source-routed forcing converges at 3.01, the projection at 1.02.

Six strategies are provided. NoForcing (free decay) and Linear (fixed-rate negative damping, Lundgren 2003) — the latter the one steady rate, folded into $\mathcal{E}$ and therefore exact and free. ConstantPower (holding the injection rate) and VarianceController (holding the field's $L^2$ observable: the kinetic energy for the velocity, the scalar variance for the scalar; the constant-$k$ controller of Bassenne et al. 2016, Eq. 20) both carry state-dependent rates and enter through the source at every stage; the controller's proportional restoring term makes its target a stable attractor rather than a clamp. ConstantPower is the default velocity forcing, chosen because it has no gain or settling time to choose (decision 95). VarianceRescaling (rescaling a band to hold the same observable — over = :band | :total) is the one post-step projection, kept as the reference implementation of a published method (Sullivan, Mahalingam & Kerr 1994) with its first-order caveat and its Berendsen-class caveat (Bussi, Donadio & Parrinello 2007) documented rather than hidden. StochasticOU (Eswaran & Pope 1988) is the one strategy independent of the flow it drives: an exact Ornstein–Uhlenbeck process on the band's conjugate mode pairs, drawn on the host, advanced on the run's backend and added at every stage, holding nothing field-sized. One implementation serves both the velocity (a vector field) and the scalar (a scalar field), because these methods are written through tensor-order-generic field operators; the only field-specific step a forcing can need is the solenoidal projection of the velocity, which the field-proportional strategies never need (each preserves a divergence-free velocity by construction) and StochasticOU applies per mode, drawing each amplitude perpendicular to its wavevector. Each forcing has a constructor taking the FixedDomain and a keyword form taking none; NoForcing, taking no domain, has only the one. The keyword form — ConstantPower(injection_rate = 0.1) — returns a DeferredForcing, materialized when Simulation builds the frame, so a case can name its forcing before the grid exists. A velocity forcing named so may also leave its strength out, and Simulation fills it from the run's predicted stationary state: the pair $(k, \varepsilon)$, given once — by kinetic_energy, dissipation, or a forcing's own target — with the other member, and the band's energy $k_{\mathrm{band}}$, predicted by predicted_stationary_state through the forcing's $\tilde{k}$ and $k_{\mathrm{band}}/k$ (decisions 95, 105). That fills Linear's rate $\varepsilon/(2k_{\mathrm{band}})$ and VarianceRescaling(over = :band)'s target $k_{\mathrm{band}}$ too. A scalar forcing is given its target: no scalar stationary state is modelled.

Which keywords carry defaults follows one test: does the value come from the method, or from the run? A canonical band (lowest_shell = 1, highest_shell = 2) is the method's, so it defaults; what a run holds fixed or drives at — target, rate, injection_rate, over, forcing_variance, the correlation time — has no canonical value and is required. A seed is neither: any value gives an equally valid realization, so one left out is drawn — from the run's rng when Simulation builds the forcing, from the global stream otherwise — and naming it is how a run is repeated (decisions 107 and 110). The deferred velocity forcing's strength above is the one relaxation, and it is the run's own: the value still comes from the run, not from a default.

4.5 Propagator — the map that advances the state in time

Propagator realizes the Mori–Zwanzig propagator: the map that carries the state forward in time, built on the generator's reversible/irreversible seam. Its numerical schemes are the Model-fibered part of the Method (§3).

  • AbstractIntegrator is the family of integrating-factor schemes dispatched by step!, which advances the velocity $\hat{\boldsymbol{u}}$ and scalar $\hat\varphi$, both in spectral representation, together through the same Runge–Kutta stages. Coupled stepping is deliberate: the scalar is passive, so time-accuracy needs both nonlinear terms evaluated at each stage's state; advancing the velocity fully and the scalar afterward would drop the substage velocities and degrade the coupling to first order.
  • IFLowStorageRK3 (the Williamson 1980 2N-storage / RKW3 workhorse) is third-order and imaginary-axis stable; IFHeun (Heun) is a two-stage option, cheaper in transforms (two nonlinear evaluations against three) but dearer in memory and imaginary-axis unstable, leaning on viscous damping. The memory comparison counts the solver's scratch registers per field: IFHeun carries three (a predictor plus two stage registers that double as its assemblies) against IFLowStorageRK3's two (an accumulator plus the assembly register). Williamson's own "2N" label counts differently — the state's array plus the accumulator, the assembly excluded as the solver's, not the scheme's (the IFLowStorageRK3 docstring keeps that ledger); the two bookkeepings agree on the point that matters, one register in IFHeun's disfavor. Two more schemes share IFLowStorageRK3's two registers: IFLowStorageRK4 (Carpenter & Kennedy 1994) is fourth-order in five stages of the same 2N-storage form, its $1.93\times$ wider imaginary-axis stability limit buying fewer transforms per unit time on a stability-limited run (decision 85); IFSSPRK3 is the Shu–Osher third-order SSP scheme in TurTLE's stage arrangement, kept for code-to-code validation against that reference (decision 80). The recommended_cfl helper gives each scheme its conservative advective-CFL ceiling $C_{\mathrm{CFL}}$ (for $\Delta t = C_{\mathrm{CFL}} \Delta x/\max_{\boldsymbol{x}}\lvert\boldsymbol{u}\rvert$, with grid spacing $\Delta x$), which the run layer uses with max_speed to choose $\Delta t$.
  • Two linear constraints are re-imposed on the advanced state at every step's exit, after the forcing's post-step projection: the divergence-free condition, by the field library's helmholtz_projection! (decision 61), and the reality condition on the real-to-complex layout's self-conjugate planes, by its reality_projection! (decision 88). Neither is held by the discretisation by construction; both are seeded at round-off and, for the reality condition, amplified by any forcing proportional to the field, so each is pinned at round-off — the reality one at exactly zero — once per step rather than left to compound.
  • IntegratorBuffers is the scheme's own per-step scratch — the Runge–Kutta stage registers, and nothing in physical representation (the substage recoveries write into the cache's slots, decision 40) — built by allocate_buffers dispatching on the concrete scheme, so each allocates exactly its working set. The right-hand-side assembly scratch lives with the generator on the ResolvedGenerator (§4.2), and the start-of-step physical fields are the observables cache's charts (§4.1): a step! is stage arithmetic over the generator protocol and the scheme's registers, nothing more. None of this scratch is state (§11 decisions 26, 30, 31).

4.6 Particles — Lagrangian instruments

Particles are instruments — probes of the turbulence — not a second physics. A particle is a state-carrying trajectory object: today a tracer (position $\boldsymbol{X}$); the deferred ladder is inertial ($\boldsymbol{X}, \boldsymbol{v}$) and oriented ($\boldsymbol{X}, \boldsymbol{v}, \boldsymbol{L}$) probes (§7). Tracers holds positions and a chosen interpolation scheme — trajectory state only, with the particle integration scheme's registers held apart in a ParticleIntegratorBuffers allocated per scheme, exactly as ResolvedFields is held apart from IntegratorBuffers on the field side (decision 50). The default scheme, Heun, is Heun-in-time on the velocity at the iteration's two endpoints. The first, $\boldsymbol{v}_1$, is the trajectory sample $\boldsymbol{u}(t_n, \boldsymbol{X}(t_n))$ recorded by the previous closing deposit — the genuine Lagrangian velocity, held in the observables cache's own velocity_at_particles slot and dated against BOTH epochs, since it is a function of the state and the positions together (read through velocity_at_particles, §11 decisions 42 and 67). The second, $\boldsymbol{v}_2$, interpolates the just-deposited $\boldsymbol{u}(t_{n+1})$ at the Heun predictor positions, which no tracer ever occupies: ParticleIntegratorBuffers.velocity_predictor is a stage register of the scheme. After the push, the particle form of deposit! interpolates the new sample at the new positions from the same deposited field and stamps it at the current epochs — one closing act per dynamical factor, step! then deposit!, advect! then deposit! — completing the iteration's deposits; interpolate_at_particles! reads any field along the trajectories for Lagrangian statistics.

The sample deposit is what keeps an instrument of $M$ tracers at $M$-point cost: depositing the sample at the particles stores $M\times3$ values where retaining the endpoint field would cost an $N^{3}\times3$ resident buffer and copy ($N$ grid points per axis). Tracked and untracked runs therefore have identical field-scale residency and per-step traffic — the zero both audits assert. (One tempting reuse is recorded as forbidden: $\boldsymbol{v}_2 \approx \boldsymbol{u}(t_{n+1},\boldsymbol{X}^*)$ differs from the next sample only at $\mathcal{O}(\Delta t^{2})$, so reusing it as the next $\boldsymbol{v}_1$ looks like a free interpolation saved — but it corrupts the recorded observable the Lagrangian statistics accumulate. Never approximate the thing you measure.)

Their numerics are first-class, on the same footing as the field schemes — and pluggable in the same way: AbstractParticleIntegrator is the family, allocate_buffers(scheme, tracers, cache) builds its registers. Two axes matter: the particle integration scheme — the default second-order Heun, and the variable-step AdamsBashforth (order 4 by default, its sample history held in the observables cache and its weight scratch in the shared ParticleIntegratorBuffers; decisions 57 and 70) for a run whose trajectory accuracy in time limits a measurement — and the sampling-consistency axis, the interpolation scheme's order relative to the field's spectral accuracy (CatmullRom by default, higher-order LalescuSpline / LagrangeSpline available). The gathers themselves visit the tracers in a memory-locality order, the ParticleTraversal — a value-preserving accelerator (the interpolated values are bit-identical with or without it) that Simulation owns beside the tracer set and rebuilds every iteration by default, the traversal_mode of its ParticleTracking choosing a manual cadence instead (decision 86). When the inertial and oriented probes arrive, the integrating-factor split carries over for the translational stiff drag (field viscosity and a particle's linear or matrix drag are the same linear-exact move), while orientation dynamics on the rotation group is a distinct geometric scheme — the reversible generator of §8 again — so the split does not naively unify all of it.

4.7 SimulationRun — the front door

A Simulation value bundles what one iteration advances and reads — the present instant (the one bounded look-back is the cache's Lagrangian sample history, which a multistep particle scheme needs): the FixedDomain, the ResolvedFields state (the fields $\hat{\boldsymbol{u}}$ and $\hat\varphi$, in spectral representation, the generator acts on), the ObservablesCache observables cache, the ResolvedGenerator (carrying the FlowConditions), the IntegratorBuffers scheme registers, the chosen AbstractIntegrator, any Tracers with its own AbstractParticleIntegrator, ParticleIntegratorBuffers and gather-order ParticleTraversal (decision 86), a stored CFL ceiling and step ceiling, and a clock. Over it:

  • Simulation(...) — the assemble-with-defaults constructor: from a grid size and a forcing it builds every piece of §4.1–§4.6, seeds a divergence-free initial condition — or adopts an existing state and tracer set outright (the injection door, decision 83) — and picks the default scheme. The viscosity is derived from the grid by default — the highest Reynolds number consistent with the chosen resolution criterion κ_max_η (decision 20; measured against the resolved cutoff, decision 82), solved from the ε of the run's predicted stationary state (decisions 95, 105) — with a supplied viscosity the opt-in override. A forcing holding ε, the default, meets κ_max_η in the stationary mean; one holding k leaves the resolution predicted through $\tilde{k}$. A forcing the model does not cover — an unforced run, a band not starting at shell 1 — has nothing to derive ν from and must supply it. Setup is a few numbers. A passive scalar and the Lagrangian tracking are each one setting value, PassiveScalar and ParticleTracking (decision 110), so neither's settings can be given to a run without the feature.
  • advance!(sim) owns one iteration: $\Delta t$ from the scheme's CFL over the cached maximum speed (scalar arithmetic — the previous closing deposit measured it), step!, the closing deposit!, the tracer advance on the sample and the deposited endpoint field, the new sample, and the deposit-completeness check. run!(callback, sim) is the loop over it, calling the stopping criterion callback once at the seeded $t_0$ and after every iteration; its Bool return decides continuation — stopping is the caller's decision on observables, never a run option (§11 decision 43).
  • StationarityCriterion is the packaged spin-up stopping criterion, and warmup!(sim; ...) its one-line sugar: stationarity detection on the running dissipation $\varepsilon(t)$ — a trailing-window flatness test that gates on $\varepsilon$ rather than on the clampable $k(t)$, though $k$ is still measured, to normalize the eddy-turnover clock $\Delta t \varepsilon/k$. The velocity-derivative skewness $S(t)$ is an opt-in second gate (gate_skewness = true; off by default since decision 78, its rank-2 transforms being a per-call cost the default path does not pay). When the scalar is forced, $\langle\varphi^2\rangle$ must settle too (gate_scalar, on by default). A fixed budget is a three-line callback, not a run option.
  • A Simulation is a container, not a reading surface (decision 49). The state is read through sim.state and the deposited observables through sim.cache, each by the accessor that owns it — kinetic_energy(sim.state.velocity_spectral), velocity_physical(sim.cache), point_positions(sim.tracers.positions) (decision 72: the raw view is GBGPeriodicFields' own accessor, not a forwarding method of this package).
  • write_simulation / read_simulation — the HDF5 checkpoint (decision 75): one self-describing group fully restores the run, recursively composed of the per-object pairs (write_domain, write_state, write_tracers, write_forcing) with the field library's write_field/write_points/write_scheme groups as the leaves. Nothing derivable is stored — the reader rebuilds through the constructor and replays the seeding deposits — and the methods live in the GBGHomogeneousTurbulenceHDF5Ext weak-dependency extension, so the surface exists only when HDF5 is loaded.
  • current_time(sim) and current_step(sim) report the run's time and step count, and the observables applied to sim.state (e.g. kinetic_energy(sim.state.velocity_spectral), dissipation on the recovered vorticity) are the current-state diagnostics, for a callback to read.

The layer wires §4.1–§4.6 together and holds no physics or numerics of its own.

4.8 Phenomenology — the reference laws (extraction-bound)

Parked since 2026-10-16 (decision 113). The module lives whole under parked/Phenomenology/ — source, oracle tests and pages, in the layout of the standalone package it becomes when extracted — and nothing in the package includes, builds or tests it; its tests run on demand with julia --project parked/Phenomenology/test/runtests.jl. What follows is the design it was built to, kept as the design of that future package.

Phenomenology is the library of reference turbulence phenomenology: the fitted scalings, model spectra, structure-function laws, and dimensionless constants that theory and experiment have established. It is the symmetric counterpart to Observables — those are the measured functions of the DNS state; these are the predicted values of the same functions. The DNS measures, the laws predict, and the comparison machine of §3 sets them side by side. Two properties follow, both instances of the charter investigate the physics, do not assume it:

  • A provider, not a comparer. A law evaluates itself from the flow parameters; it knows nothing of the DNS. The comparison lives consumer-side — the caller's own analysis, or a test suite — reading both; the package ships no comparer.
  • No parametrization is privileged. A published fit and one of our own are the same kind of object — subtypes of one law family, discovered and validated alike, never baked in as truth.

The abstraction is the strategy pattern already used for AbstractForcing / AbstractIntegrator / DealiasingStrategy: a law family is an abstract type, each parametrization a named preset — usually a concrete subtype carrying its fitted coefficients and provenance, or (for the composed velocity spectra) an alias naming the ModelSpectrum specialization that carries its two roll-off factors, so isa holds on the preset name either way (decision 55) — implementing one small interface: evaluate the law at its argument ($\kappa$, $r$, $\mathrm{Re}_\lambda$) given a FlowParameters bundle; report its provenance (the citation and validity range); and eventually fit itself to data. Choosing a law is choosing the preset (Pope2000 versus VonKarman1948) and optionally overriding its coefficients (Pope2000(; C_K = 1.6), the published fit being the default). Provenance is first-class — the comparison needs a law's validity range to be fair, and it is the single source of the citation.

Naming is a three-level handle, because one author publishes many models across years and quantities: the quantity is the submodule (Spectra.Pope… versus StructureFunctions.Pope…), the paper is the author-year handle (Pope2000, first author's surname, the full list in provenance), and a same author-year-quantity collision takes a trailing letter (Pope2014a, Pope2014b). The full handle Phenomenology.Spectra.Pope2000 reads like a citation and is unique by construction — and where a preset's value is not read off its name's paper (Sreenivasan1995's as-quoted value), the docstring says so at the value.

Submodules are cut by representation, so they stay few while the models multiply as subtypes:

  • Spectra — functions of $\kappa$ (velocity $E(\kappa)$, scalar $E_\varphi(\kappa)$), composed: an inertial core $C_K \varepsilon^{2/3}\kappa^{-5/3}$ times a swappable large-scale factor $f_L(\kappa \ell)$ — each form evaluated at the length its own coefficient was fitted against — and dissipation-range factor $f_\eta(\kappa\eta)$, a named preset fixing a published triple.
  • StructureFunctions — functions of $r$ (the $D_{L\dots}(r)$ laws and, sharing the representation, any two-point correlation law when one is added).
  • Scalings — the dimensionless numbers and their $\mathrm{Re}_\lambda$ trends: the Kolmogorov constant $C_K$ (Sreenivasan1995) and the normalized dissipation constant $C_\varepsilon$ (Sreenivasan1998). The derivative skewness, the flatness, the Lagrangian $C_0$, and the mechanical-to-scalar timescale ratio are forward-looking additions to the family, not yet built.

Three exist now — enough for the validation checklist — and the count caps near six: PDFs, Decay ($k \sim t^{-n}$), and Lagrangian are named future seams, not owed — named here rather than in §7, which lists the deferred capabilities rather than the submodules that would carry them. A single FlowParameters bundle carries the quantities a law reads ($\varepsilon$, $\nu$, $L_{11}$, $u'$, $\mathrm{Sc}$, $\varepsilon_\varphi$), with the derived scales ($\eta$, $\tau_\eta$, $\lambda$, $\mathrm{Re}_\lambda$, $\varkappa$) as helpers — the analogue of the FlowConditions and FixedDomain bundles.

The laws are compared against, never consumed by the solver (decision 112): the comparison is the module's own test, and the dynamics binds nothing the module defines. And the loop closes: we measure (with this package and SS), fit a parametrization to that measurement, and the new fit lands beside the literature, to be validated against the next run.

Formula verification. A transcribed law is checked not against a reference implementation — none is authoritative, and cross-checking against another code merely moves the trust — but against the physical relations it must satisfy: the asymptotic slopes (the $\kappa^{-5/3}$ inertial range, the low-wavenumber $\kappa^\sigma$, the dissipation cutoff), the $\zeta_3 = 1$ constraint on every intermittency model, and the roll-off limits $f_L, f_\eta \to 1$. This self-consistency battery lives in the test suite and catches a wrong exponent, coefficient, or sign without trusting a second source.

Extraction requirement (recorded). Phenomenology is designed to be cut into a standalone GBGTurbulencePhenomenology with no rewrite — the demand-driven path that extracted GBGStreamingStatistics. The requirement constrains the design. It is a dependency-light leaf, depending on neither GBGPeriodicFields (a law is a scalar function, no field math) nor GBGStreamingStatistics (it provides reference values, computes no statistics) nor this package's dynamics, and its pages form their own group, separable from the DNS surface. Extract when a consumer appears (decision 18).

4.9 Layout summary

SimulationDomain → Observables → State → Cache → Forcing → Generator → Propagator → Particles → SimulationRun. Cross-module access is through explicit using ..Module: name lists. The reference-law module Phenomenology (§4.8) is parked outside the package and outside this order. Statistics live consumer-side of this package too: the sampling in Particles and the observables in Observables produce the samples, and a statistics bridge that streams them to GBGStreamingStatistics is deferred (§7).

5. The consumer boundary — what belongs here, and what does not

GBGHomogeneousTurbulence owns the turbulence-specific glue and delegates everything domain-neutral. The dividing line is domain-neutrality, not "thinness":

  • To GBGPeriodicFields — every field operation: the transforms, curl! / cross! / divergence!, the Leray–Helmholtz projection helmholtz_projection! ($\mathbb{P}$), convolve! and the dealias/band kernels, the reductions (inner, the radial spectrum and correlation), and grid↔point interpolation. The rule everything diagonal in Fourier is a GBGPeriodicFields operator is followed in the code.
  • To GBGStreamingStatistics — every estimator: histograms, densities, conditional means and variances, conditional and transition densities.
  • Owned here — the Navier–Stokes and scalar nonlinear assembly, the integrating factor, the forcing strategies, the coupled time-stepping, the particle tracking, the run layer, and the turbulence-specific spectral glue a backend must not carry (the deferred sheared frame's non-separable multipliers, §7).

Two standing rules follow:

  1. If a capability's true home is GBGPeriodicFields or GBGStreamingStatistics, raise it and extend it there — do not reimplement it here. Only genuinely domain-neutral capability migrates out; a backend has an anti-accretion charter, so turbulence-specific glue stays here.
  2. A deferred-by-design future is not a missing feature (§7).

6. Precision and footprint as studied axes

Precision and the memory-footprint/accuracy trade-off are objects of study, not fixed defaults — the numerical counterpart of the charter that the tool investigates the physics rather than assuming it (§8).

  • Both precisions are supported equally, and no kernel privileges either. (The Simulation constructor must start somewhere and starts at Float64 / Array; that is a convenience constructor's choice, not a property of the library, and FixedDomain takes both from the caller.) Float32 buys twice the grid per byte and roughly twice the throughput on a consumer GPU; Float64 buys the accuracy margin a long integration or a sensitive diagnostic may need. Which one a run wants is a fitness question, settled by test rather than by a house default. The element type $T$ flows from the frame (§4.1): no kernel silently fixes the arithmetic. (The FlowConditions scalar parameters are stored Float64 and converted to $T$ at use — a scalar convenience, not a field commitment.) Field reductions do not break this: every observable returns the field's own element type, so a Float32 run measures in Float32 — the Observables module docstring states it and test/validation.jl pins it over every exported observable. Accuracy is bought there by summation order, not by a wider accumulator: the backend's reductions sum pairwise, whose error grows as

$O(\log n)$ against naive accumulation's $O(n)$, so a reduction over an $N^3$ grid stays faithful in the field's own precision and needs no Float64 accumulator to rescue it. Whether the online statistics of a future GBGStreamingStatistics bridge should accumulate in Float64 regardless is a question for that backend, not a property of this one.

  • The footprint/accuracy trade-off is held at both ends — low-storage integrators, the dealias fraction, truncation — and the working point is chosen by direct fitness test, never decreed. Which precision, order, or footprint suffices for a regime is a measured finding.
  • The fitness arbiter is the comparison machine of §3 — the same one that adjudicates method-independence and DNS-versus-LES statistical commutation. One machine ranges over model fidelity, scheme, precision, footprint, and closure; the sufficiency frontier (the cheapest realization that still passes) is a deliverable of the tool.

This is why the GBGPeriodicFields element-type genericity and GPU-first, allocation-free discipline are load-bearing here: they are what make precision and backend free to vary, and they are what keep the state a compile-time product of concretely-typed buffers (§9, invariant 4). "Low footprint" is the default working point on a studied axis, not a universal law.

7. Deliberately deferred

These are named so they are not precluded, and deliberately left un-abstracted: no extension point or generalization is built for them until a second concrete case forces the abstraction. None is a gap.

  • The uniform-mean-gradient scalar source — the standard scalar-injection route ($-u_i \partial_{x_i}\langle\varphi\rangle$ with an imposed mean gradient), the missing piece of the mean-gradient mixing System named in §3. A forcing-strategy slice, not a frame change.
  • Stochastic (Eswaran–Pope OU) forcing — DELIVERED (decision 90). Archived while its dense form drew a field of noise on the host every step; returned as a coarse companion field, with its process in the run's state.
  • Checkpoint / exact restart to HDF5 — DELIVERED (decisions 75, 90). Five writer/reader pairs, composed recursively on the field library's persistence groups, restore a run that continues bitwise (§4.7), a stochastically forced run included: its process and its position in the stream are part of the stored state.
  • Inertial and oriented particles — $(\boldsymbol{X},\boldsymbol{v})$ with matrix drag, then $(\boldsymbol{X},\boldsymbol{v},\boldsymbol{L})$ with torque. The translational drag reuses the integrating-factor split; orientation needs a geometric scheme (§4.6, §8).
  • The sheared frame (Rogallo), a ShearedDomain. A uniform mean velocity gradient makes the wavenumbers time-dependent ($\mathrm{d}\boldsymbol{\kappa}/\mathrm{d}t = -\boldsymbol{A}^{\!\top}\boldsymbol{\kappa}$) and non-separable — the SimulationDomain counterpart to FixedDomain (§4.1). This is the one future with a concrete GBGPeriodicFields dependency: its separable per-axis multipliers cannot hold a sheared lattice, so it is a bounded extension there (rule 1 of §5), not a job here.
  • The Model ladder beyond DNS — a large-eddy Model (filter the DNS, model the subgrid stress) and a filtered-density-function or moment Model (§8). Each is a coarser projection on the ladder of §3, and the four roles are already carved to receive it — but, per invariant 9, no generality is built until a second rung forces it. Each is discriminated from DNS by statistical commutation; the canonical acceptance test is the relaxation of a two-mode scalar distribution (a micromixing benchmark). The natural first spectral rung is a Chollet–Lesieur eddy viscosity $\nu_e(\kappa \mid \kappa_c)$ at the truncation wavenumber $\kappa_c$ (Chollet & Lesieur 1981) — architecturally a per-mode linear rate, a negative linear-forcing citizen folded into the integrating factor as the steady rate of a Linear forcing is, with the plateau–cusp profile resident and only its $\sqrt{E(\kappa_c)/\kappa_c}$ scale updated per step from one shell reduction. The Hou–Li filter at $\nu = 0$ is its crude implicit sibling (numerical-dissipation LES), with the known cutoff-bottleneck caveat.
  • The statistics bridge — the sampling-to-GBGStreamingStatistics path (Eulerian field samples and Lagrangian trajectory samples in, streamed summaries out).
  • Alternative dealiasing and nonlinear forms (partly built). DealiasingStrategy now owns the dealiased nonlinear assembly — $\hat{\boldsymbol{u}}$ (and $\hat\varphi$) in, the dealiased term out — so a strategy may restructure how the product is computed, not merely filter its output. The sharp $2/3$ rule and the smooth Hou–Li filter kernel-multiply the single realization; PhaseShift (decision 27) averages a half-cell-displaced evaluation to cancel aliasing and truncates spherically to $\tfrac{\sqrt{2}}{3}N\cdot\tfrac{2\pi}{L}$, at $2\times$ the transforms. Still deferred siblings of the same assembly: $3/2$ zero-padding, and the skew-symmetric momentum form (which reorganizes the quadratic product to conserve energy in the discrete equations). The assembly touches only the Generator and its scratch, never the State (§4.1); the rotational form + spherical $2/3$ stays the lean default.
  • A temporal-accuracy step control. The step is set today by the advective CFL — a stability-calibrated, conservative ceiling with a manual cfl override — and nothing adapts it to a target temporal accuracy. An embedded-error or PI step controller, distinct in purpose from the stability CFL, would make temporal accuracy a studied fitness axis beside precision and footprint (§5). Deferred: HIT runs are typically stability-limited near the CFL ceiling, so a fixed step at the CFL is rarely the accuracy bottleneck.
  • The $\nu = 0$ truncated-Euler experiment — a scheme and dealiasing oracle. At zero viscosity (accepted today; the integrating factor degenerates to the identity) the sharp-masked assembly is the exact Galerkin truncation of the Euler equations, which conserves kinetic energy in continuous time — so measured energy drift isolates the time scheme alone: a conservation and order-of-accuracy test on IFLowStorageRK3 (the drift must scale with the scheme's order; at $\nu = 0$ IFHeun is excluded — its stability rests entirely on viscous damping, which the oracle removes, so it would measure an instability, not an order), a second witness that the sharp-cutoff strategies (TwoThirds, PhaseShift) are exactly Galerkin (an alias residue breaks the detailed conservation of the retained triads), and a direct measurement of the Hou–Li filter's effective dissipation (the one deliberately non-conservative strategy). The long run is a validation target of its own: the truncated system thermalizes toward absolute equilibrium — an equipartition $E(\kappa) \propto \kappa^{2}$ tail growing from the cutoff, the thermalized tail acting on the large scales like an eddy viscosity while it grows (Cichowlas et al. 2005). It is not a turbulence run — the dissipation-based diagnostics degenerate ($\varepsilon \to 0$, $\mathrm{Re}_\lambda$ undefined) — and it is deferred as a test, not a capability.

8. Lenses and prior art

One piece of prior art is excluded outright: the previous generation of this work (the private OldCode archive among the study-only clones). It is not among the lenses below and is not a source of design. It is retained only as a record to interrogate: what was done before, and what came of it. The direction of the GBG packages is to replace it entirely, because it was problematic, and this architecture is the replacement rather than a refinement of it. It follows that nothing here is justified by continuity with it — an arrangement it shared is neither evidence for nor against the arrangement here, and must stand on the reasoning in this document (the same rule §11 applies to a recorded decision: legacy is not evidence of correctness). Where it is consulted, the product is a diagnosis, not a pattern.

The package makes real theory legible. One framework — Mori–Zwanzig — is its foundation (§3); the rest are lenses read through it. Nothing in the numerics is load-bearing on the subordinate lenses — the arithmetic would be identical had they never been named — but the architecture is founded on the Mori–Zwanzig decomposition, which is exact and so can carry that weight. The lenses organize understanding and set what the tool is built to investigate, not assume.

  • Mori–Zwanzig — the foundation, elaborated. §3 states the decomposition; here is its machinery. A projection $\mathcal{P}$ splits the full state into a resolved part and the rest, and applying it to the exact dynamics gives the resolved variables a generalized Langevin equation (Mori 1965; Zwanzig 1973): a streaming term (the projected drift), a memory integral over a kernel $K(t-s)$ carrying the history the projection discarded, and a colored-noise term living in the unresolved subspace. A Model is a choice of $\mathcal{P}$ and a closure that approximates that kernel and that noise; DNS is the identity projection, for which both vanish, so it needs no closure. The memory kernel $K$ is the precise content of the tendency a coarse state cannot supply on its own (§3), and modeling it is the closure problem the tool exists to test.
  • Open systems / non-equilibrium — a reading of the projection. The Mori–Zwanzig cut is the open-system system/environment split: the resolved variables are the system, the projected-out variables the environment, which survives only as the memory + noise above. A driven-dissipative flow is an open system in a non-equilibrium steady state — energy injected by the forcing (an energy reservoir, the source of §4.2), dissipated to the unmodeled viscous bath (the sink), balanced at stationarity. The lens carries its own caveat: whatever a model retains of the environment — a stochastic forcing's internal state, a closure's subgrid degrees of freedom — is not the environment but the finite Markovian surrogate kept on the system's own side, a modeled degree of freedom; so it homes as the modeled slot on the one State, never a separate "environment state" — built for the stochastic forcing's process (§11 decision 90).
  • The commuting square — the modeling ideal. With $\Pi$ a coarse-graining and $S$ a flow map, one would like $\Pi\circ S_{\mathrm{fine}} = S_{\mathrm{coarse}}\circ\Pi$. It cannot hold pathwise: the coarse state does not determine its own tendency (that is the memory and noise made concrete), and turbulence is chaotic. The achievable ideal — the design target of any Model — is statistical commutation, agreement of the distributions and fluxes on the attractor, exactly what the DNS-versus-LES comparison of §3 measures.
  • Geometric mechanics (metriplectic / GENERIC) — the reversible/irreversible split. The integrating-factor method is a split into a reversible generator (the advection, in rotational form, §4.2) and an irreversible one (the diffusion, integrated exactly). Read as a metriplectic system — a Hamiltonian (symplectic) bracket generating the reversible part, a dissipative (metric) bracket the irreversible — the lens says why the split is structure-preserving and constrains every closure to be net-dissipative. Here it is a lens rather than a literal thermodynamics: isothermal incompressible flow has no genuine entropy (§4.2). The term is Morrison's (1986; metric + symplectic); Öttinger's (2005) GENERIC is the same structure.
  • Renormalization / scale invariance — a hypothesis, never a foundation. Small-scale universality is what would make closure constants transferable, but it is approximate (intermittency), it fails for scalar small scales (persistent gradient anisotropy), and the unclosed terms are conditional quantities that re-import the large scales. So the tool is built to test how universal a closure is, per regime, not to assume it. This is the general charter: the architecture investigates the physics; it must not assume it — the same discipline as the model-free statistics it consumes.
  • The skew-product tower — what a Simulation is. The composite system factors as a tower $t \to$ forcing noise $\to$ fields $\to$ particles: the generator is block lower-triangular (each row reads only itself and the rows above — the fields never read the tracer positions, the clock reads nothing), so the flow is a skew product and advance! is its Gauss–Seidel sweep in topological order (step the fields, refresh the cache, push the tracers, tick the clock). Triangularity is what licenses the composed propagator: splitting error cannot propagate up the triangle. It also gives every state slot a litmus. The restart record holds exactly what the flow map needs — $\hat{\boldsymbol{u}}$, $\hat\varphi$, the tracer positions, and a stochastic forcing's internal state (the extended-phase-space discipline of molecular dynamics' thermostats). The observables cache holds spent compute, reconstructable from the record — delete it and the trajectory is unchanged. The clock and what a run records are the experimenter's logbook rather than physics. The ObservablesCache charts are the tower's algebraic variables — solved, never integrated — and their per-factor epochs inherit the triangle: a chart is stale against exactly the factors it reads.

9. Invariants — the deliberate absences

The public surface and these absences are the spec. Do not add a capability "for completeness"; a missing one usually encodes a decision.

  1. No physical units. Quantities are dimensionless, on the box's order-one reference scales; control is by $\mathrm{Re}$ (through $\nu$) and $\mathrm{Sc}$, and the reference constants a run is judged against — $C_K$, $C_\varepsilon$, and the kinetic energy in box units $\tilde{k} = k/(\varepsilon L)^{2/3}$ — are dimensionless groups.
  2. No field or statistics machinery reimplemented. Field operations come from GBGPeriodicFields, estimators from GBGStreamingStatistics (§5).
  3. No privileged precision or backend. $T$ and the array type flow from the frame; both precisions and CPU/GPU are first-class (§6).
  4. Allocation-free stepping over a compile-time state — with an audited footprint. A time step allocates no field-sized memory over the preallocated IntegratorBuffers — load-bearing for GPU hot loops. The evolving state is a compile-time product of concretely-typed buffers (a parametrized record the compiler specializes), never a runtime-heterogeneous container — the discipline that keeps the step type-stable and device-generic, and that lets the state grow (a scalar today, a coarser Model's extra fields tomorrow) to more slots at no runtime cost. Each scheme allocates exactly its working set: allocate_buffers dispatches on the concrete scheme and builds only the registers that scheme writes — there is no over-allocating ::AbstractIntegrator fallback, so a scheme with no method is a hard error, never a silent superset (an IFLowStorageRK3 run carries neither of the two registers IFHeun adds — its corrector stage and its velocity predictor).
  5. GPU-first, single-node, backend-agnostic. Shared-memory only; no distributed or multi-GPU scope (inherited from GBGPeriodicFields).
  6. No baked-in physical model, closure, or universality assumption. The tool investigates these; it does not assume them (§8). The Mori–Zwanzig foundation is exempt because it is exact, not a model — a projection is an identity, and what remains modeled is the closure the tool is built to test (§3).
  7. A library, not a framework. The run layer is a convenience over exposed pieces (§2, §4.7), never a mandatory shell.
  8. The scalar is denoted $\varphi$, never $\theta$ — in code, mathematics, and prose. And it is an $\mathrm{Sc} = O(1)$ scalar: no Batchelor-range machinery exists, the derived viscosity resolves the velocity's cutoff rather than $\eta_B = \eta/\sqrt{\mathrm{Sc}}$, and the constructor warns — never refuses — when the scalar is clearly under-resolved. High-Schmidt support is a deliberate absence, not an oversight.
  9. Deferred futures are accounted for, not owed (§7); no speculative extension points.

10. Conventions

  • Docstrings are operator-first, then scheme. State the continuous operator or PDE term and its exact/ideal form, then the discrete realization — as velocity_integrating_factor leads with $\partial_t f = D\nabla^{2} f$ before $\mathcal{E}(\boldsymbol{\kappa})$, and velocity_rhs! with the Lamb-vector identity before the pseudospectral product. This is the turbulence analogue of the siblings' physical-form-first / estimand-first rules.
  • Coordinate-free where a coordinate-free form exists. Homogeneous isotropic turbulence is statistically isotropic — no preferred direction — so a diagnostic or computation that picks a coordinate axis imports a spurious direction-dependence; state the rotation-invariant form, not an axis projection. The reference is derivative_skewness: the normalized third invariant of the strain rate $\boldsymbol{S}$, not the axis-picking longitudinal velocity-derivative skewness (decision 17).
  • Two-tier docs. CLAUDE.md is the terse working map and defers here; this document carries the rationale and the decision log. Mathematics is rendered LaTeX in the glossary's notation (docs/src/notation.md); a code identifier is always in backticks and never inside a math span; each code object is bound to its mathematical symbol on first mention — rendered as one LaTeX span, $\texttt{dissipation} \equiv \varepsilon$.
  • No dead references on the user-facing surface. A rendered docstring — and a thrown error — must read complete at the REPL, where cross-links are dead: it cites no section number (§4.5), decision-log entry, or repo path. Design rationale and section citations stay in # comments and this document.
  • Cross-referencing is discriminating-minimalist. A link earns its place: promote a backticked identifier to @ref / @extref only for a genuine jump with one clear destination; link a target at most once per docstring; never link the docstring's own binding, its arguments, or bare Base names — except the storage-backend / element types and GBGPeriodicFields objects, which @extref to their own package docs (the DocumenterInterLinks setup).
  • Verification is by numerical oracle, not a formalization ledger. Because the package introduces no novel mathematical objects (they are GBGPeriodicFields' and GBGStreamingStatistics'), its nontrivial claims are dynamical — the exactness of $\mathcal{E}$, the order of the scheme, imaginary-axis stability, mean conservation — and are pinned by numerical oracle tests (a Taylor–Green order study, unforced energy decay, exact diffusion). This is why the package follows the GBGCloudPhysics consumer pattern with no FORMALIZATION.md; a typed-statement ledger is a backend's need. The design's structure — the module carving and role wiring — was checked at design time against a relational-logic model (decisions 21–22), which carries no dynamics and so complemented the oracle rather than becoming the ledger. Revisit only if a built Model rung introduces genuinely package-specific formalism.
  • Category/type errors are their own correctness class. A claim can be perfectly formatted and read true yet conflate two kinds of object — a field with its representation (physical vs spectral); a diagnostic scalar with the field it reduces (the rate $\varepsilon$, a number, vs a dissipation field; $k$ vs the spectrum $E(\kappa)$); an operator with its parameter ($\mathcal{E}$ vs $\nu$; $\mathbb{P}$ vs $\mathcal{P}$); a rate with its time-integral; a spectral density $E(\kappa)$ with an energy. Type each object from the code and expand the statement — the physics mirror of the sibling backends' type-error guard (GBGStreamingStatistics' density-vs-measure, estimator-vs-estimand).
  • The /check-docs battery. Documentation quality is enforced by a full matrix — (Correct / Self-contained / Notation / Formatted / Current / Cited / variant-pairs) × (every surface: ARCHITECTURE.md, every src/*.jl docstring, every docs/src page) — run to completion in one pass (.claude/commands/check-docs.md). Correct extends to physical-formula and normalization checking (the $1/N$, the $2\varkappa$, the $\tfrac{1}{2}$ in the energy, Parseval factors) and to the category/type-error class above. The rulebook's programs and checkdocs = :exports are the mechanical backstop.
  • Citations follow author–year; the full references are §References. Never cite an inaccessible source; the material under inspiration/ is private and never referenced. A reference block of two or more citations is a bullet list — one citation per line — never a semicolon-joined paragraph.
