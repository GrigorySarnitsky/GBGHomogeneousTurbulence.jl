Particles

GBGHomogeneousTurbulence.Particles — Module
Particles

It tracks Lagrangian particles, today the massless tracer:

  • Tracers — the tracer set: the positions (a PointSet), a selectable interpolation scheme, and opt-in unwrapped positions read by unwrapped_positions. The velocity at the particles is read from the run's observables cache through velocity_at_particles.
  • AbstractParticleIntegrator — the particle integration schemes, Heun and AdamsBashforth; ParticleIntegratorBuffers the per-step storage a scheme needs, and history_depth the length of the velocity-at-particles history a scheme requires.
  • deposit! — this module adds the particle method: interpolate the flow velocity at the tracers' current positions and deposit it in the observables cache. One value has two consumers: the Lagrangian statistics a caller accumulates, and the next advance, which reads it as its start-of-step velocity.
  • advect! — advance the trajectories one step under the chosen scheme; restart! discards a scheme's history after the tracers are repositioned from outside the iteration.
  • interpolate_at_particles! — read a field at the particle positions; new_vector_point_values / new_scalar_point_values allocate the output buffers it fills.
  • ParticleTraversal — the memory-locality order the gathers visit the tracers in, a value-preserving accelerator; rebuild_traversal! refreshes it from the current positions.
  • write_tracers / read_tracers — the tracer set's HDF5 persistence: positions, the opt-in unwrapped positions, and the interpolation scheme as one self-describing group (available once HDF5 is loaded).
source

The tracer set

Tracer positions plus a selectable interpolation scheme, with the accessors that read a tracer set's state — its positions and its count. The set holds trajectory state only; a scheme's working storage lives apart.

GBGHomogeneousTurbulence.Particles.Tracers — Type
Tracers(domain; number_of_particles, interpolation_scheme, unwrapped = false,
        rng = default_rng())
Tracers(domain; positions, interpolation_scheme, unwrapped = false)

A set of Lagrangian tracers, built on domain's backend and element type.

Give exactly one of the two. The number_of_particles form seeds that many tracers uniformly at random in the periodic box. The positions form supplies the tracer positions as a GBGPeriodicFields PointSet, copied to domain's backend and element type. Supplying both, or neither, raises an ArgumentError, and so does a raw array in place of the PointSet: coordinates cross into the package only through the GBGPeriodicFields point types.

The interpolation_scheme is the GBGPeriodicFields scheme used to evaluate the velocity — and any sampled field — at the tracer positions. CatmullRom is the $C^1$ choice and Simulation's default; it is a ready-made value rather than a type, so it is passed bare. LalescuSpline and LagrangeSpline offer higher smoothness or interpolation order at a wider stencil — useful for derivative-sensitive readouts such as acceleration statistics. Each takes its stencil width in grid points per axis (CatmullRom is LalescuSpline(4)), and LalescuSpline also takes its order of continuity as the smoothness keyword.

Arguments

  • domain — the FixedDomain whose backend, element type and box the set is built on.
  • number_of_particles — seed this many tracers uniformly at random in the box.
  • positions — or copy this PointSet in instead; give exactly one of the two.
  • interpolation_scheme — the scheme used to evaluate a field at the tracer positions.
  • unwrapped = false — set to true to also track the winding-preserving unwrapped positions unwrapped_positions serves; the wrapped positions stay the dynamical state either way.
  • rng — the random stream seeding the positions (used with number_of_particles, ignored with positions); defaults to Random.default_rng().

Examples

A run carries tracers when Simulation is given a count; advance! then advances them with the fields and records the Lagrangian velocity each iteration, so both reads below are current between iterations:

sim = Simulation(grid_points_per_axis = 64, scalar = PassiveScalar(),
                 particles = ParticleTracking(number_of_particles = 4096))
advance!(sim)

# the (M, 3) positions, via GBGPeriodicFields
X = point_positions(sim.tracers.positions)
# u(tₙ, X(tₙ)), the Lagrangian velocity — throws if stale
v = velocity_at_particles(sim.cache)

out = new_scalar_point_values(sim.tracers)  # allocate once, then reuse every iteration
interpolate_at_particles!(out, scalar_physical(sim.cache), sim.tracers)

Building a set directly — to place tracers deliberately rather than at random, and to advance them by hand — takes the positions form, and then the scheme's per-step storage is yours to allocate:

tracers = Tracers(domain; positions = PointSet([0.1 0.2 0.3; 1.0 1.0 1.0]),
                  interpolation_scheme = CatmullRom)
cache   = ObservablesCache(domain; number_of_particles = npoints(tracers.positions))
buffers = allocate_buffers(Heun(), tracers, cache)

# u(tₙ) at the current positions — do this first
deposit!(cache, tracers, u)
advect!(Heun(), tracers, u_end, domain, buffers, dt)

Read the particle state straight off the struct's own fields — the positions are PointSets, and raw arrays and counts come from GBGPeriodicFields' point_positions and npoints, never from accessors of this package. Passing unwrapped = true additionally tracks the winding-preserving unwrapped positions unwrapped_positions serves — the wrapped positions stay the dynamical state either way. The velocities are a deposited observable, not tracer state: the particle form of deposit! writes them into the run's observables cache at the end of each iteration, and velocity_at_particles reads them there.

The particle integration scheme's own working storage is not here: it lives in a ParticleIntegratorBuffers, whose docstring explains the split.

Fields

  • positions — the tracer positions, as the PointSet every operation takes: the one storage, always wrapped — the dynamical state. GBGPeriodicFields' point_positions serves its (M, 3) matrix view, with $M$ the tracer count.
  • interpolation_scheme — the scheme used to evaluate a field at the tracer positions.
  • unwrapped_positions — the opt-in unwrapped positions (unwrapped = true) as a PointSet, advanced by every push with the same displacement terms but never reduced to the box; nothing when untracked. Read it through unwrapped_positions.
source
GBGHomogeneousTurbulence.Particles.unwrapped_positions — Function
unwrapped_positions(tracers)

The unwrapped positions of the tracer set tracers, as a PointSet — the trajectory with its winding kept, each coordinate the literal sum of every displacement since seeding, never reduced to the periodic box. These are the positions a mean-square-displacement or dispersion diagnostic needs: those are functions of the displacement $\boldsymbol{X}(t) - \boldsymbol{X}(0)$, with $\boldsymbol{X}$ a tracer's position, which box-wrapped positions cannot supply across a crossing. Accumulating such statistics over them — on the raw (M, 3) array GBGPeriodicFields' point_positions extracts — is the caller's analysis.

The unwrapped positions exist only when the tracer set was built with unwrapped = true; reading an untracked set throws an ArgumentError (which is why this throwing read exists while the plain state is read straight off the struct's fields). The wrapped positions remain the dynamical state either way — the dynamics always advance wrapped, since a coordinate that grows with winding loses absolute floating-point resolution, while the unwrapped positions only ever feed differences, whose relative accuracy the growth does not touch. An announced reposition (particles_modified! on a run) restarts the unwrapped positions at the wrapped ones: winding is a property of the trajectory just abandoned.

The particle integration scheme

How the positions are advanced over one step — the Lagrangian counterpart of the field schemes. Heun reaches second order with a second interpolation per step; AdamsBashforth reaches further by reusing the Lagrangian samples already deposited, at no extra interpolation. Each scheme's storage is allocated by allocate_buffers, which a run calls for you.

GBGHomogeneousTurbulence.Particles.AbstractParticleIntegrator — Type
AbstractParticleIntegrator

The supertype of the particle integration schemes — how the tracer positions are advanced over one step, the Lagrangian counterpart of the field side's AbstractIntegrator. A scheme is a value (Heun()), passed to advect! and to allocate_buffers, which builds exactly the working storage that scheme needs.

The family has two members today: Heun, a one-step method that buys second order with a second interpolation, and AdamsBashforth, a multistep method that buys more by reusing the Lagrangian samples the run already deposits. Which trade a run wants is for its user to measure — one interpolation per step against one stored array per extra order.

source
GBGHomogeneousTurbulence.Particles.Heun — Type
Heun()

Second-order Heun-in-time on the velocity at the two ends of the step — the particle integration scheme a run uses by default. It advances the positions with the start-of-step Lagrangian velocity the previous iteration's closing particle deposit! left in the cache and the end-of-step velocity field the solver has just produced, so it needs nothing from inside the field scheme's stages.

It needs one set of predicted positions and the velocity interpolated there (ParticleIntegratorBuffers). One step of advect! over $\Delta t$ is

\[\begin{aligned} \boldsymbol{v}_1 &= \boldsymbol{u}(t_n, \boldsymbol{X}), & \boldsymbol{X}^{*} &= \boldsymbol{X} + \Delta t \boldsymbol{v}_1, \\ \boldsymbol{v}_2 &= \boldsymbol{u}(t_{n+1}, \boldsymbol{X}^{*}), & \boldsymbol{X} &\leftarrow \boldsymbol{X} + \tfrac{\Delta t}{2}(\boldsymbol{v}_1 + \boldsymbol{v}_2), \end{aligned}\]

with positions wrapped into $[0, L)$, $L$ the box side.

Pair it with the default interpolant unless the grid is coarse

Under the advective-CFL loop $\Delta t \propto \Delta x$, so this scheme's error falls as $\Delta x^{2}$ while a degree-$d$ interpolant's trajectory floor falls as $\Delta x^{d+1}$. For the default CatmullRom (degree 2) the floor therefore falls faster than the time error, and the two cross over: measured on a band-limited field of $N$ grid points per axis, interpolation dominates at $N = 16{-}32$ and the time error dominates from $N \approx 64$ on (at $N = 128$ the floor is $1\times10^{-5}$ against a time error of $6\times10^{-5}$; the numbers are setup-specific, and only the $\Delta x^{d+1}$ trend generalizes). So at production resolutions CatmullRom is not what limits a Heun trajectory and a wider stencil buys nothing; at coarse resolution, or with $\Delta t$ cut well below the CFL value, LalescuSpline(8; smoothness = 1) — same $C^1$, degree 3 — moves the floor down by more than an order of magnitude. What governs this in a run is how well the grid resolves the Kolmogorov length $\eta$, so read $N$ here as a stand-in for $\kappa_{\max}\eta$, with $\kappa_{\max}$ the largest resolved wavenumber.

GBGHomogeneousTurbulence.Particles.AdamsBashforth — Type
AdamsBashforth(; order = 4)

Variable-step Adams–Bashforth trajectory integration — the scheme TurTLE uses for its tracers, at its default order (Lalescu et al. 2022) — buying accuracy in time at no extra field evaluation and no extra interpolation per step.

Use it in place of Heun when trajectory accuracy in time limits a measurement. Heun buys its second order by interpolating a second time, at predicted positions; Adams–Bashforth instead reuses the Lagrangian samples the run has already deposited at earlier instants. The trade is one stored array per extra order against one interpolation per step. One step of advect! is

\[\boldsymbol{X} \leftarrow \boldsymbol{X} + \sum_{j=0}^{K-1} b_j \boldsymbol{u}(t_{n-j}, \boldsymbol{X}(t_{n-j})),\]

with $K$ the order and the weights $b_j$ re-solved each step by integrating the Lagrange basis on the recorded step history.

The steps are not assumed uniform: the advective-CFL loop changes $\Delta t$ every iteration, which classical fixed-step coefficients would silently get wrong, so the weights are recomputed each step from the actual step history. That is $\mathcal{O}(\texttt{order}^2)$ host arithmetic per step, independent of the tracer count.

A multistep method has no history at $t_0$, so the first order - 1 steps are taken with Heun and the scheme then switches over; the same restart happens if the tracers are reseeded. Those second-order starting steps leave a fixed error behind, so over a fixed window order = 4 converges at about third order rather than fourth — on a smooth test problem, $3.0$ against $2.0$ for the two-step method, with an error some fifty times smaller at equal step count. A higher-order start would need the velocity between the step endpoints, which the solver does not produce.

Arguments

  • order = 4 — how many past samples are used. 1 is forward Euler, 2 the two-step method, 4 TurTLE's default. Orders above 8 are refused with an ArgumentError: past it the four-point Gauss–Legendre rule that integrates the interpolation weights stops being exact, and the refusal is loud because the alternative is silently wrong weights. The cap is far above any useful order, since an Adams–Bashforth stability region shrinks with each step added — and the bootstrap makes high orders worse, not just useless: over a fixed window, order = 6 and order = 8 measure the same third-order convergence as order = 4 with larger errors (measured $1.0$ and $1.4$ against $0.6$, in units of $10^{-7}$ at 80 steps: the longer Heun bootstrap costs more than the extra history returns). The practical ceiling is order = 4.
The interpolant sets a floor no timestep can cross

Interpolating the velocity perturbs the field the tracers follow, and that perturbation does not shrink with $\Delta t$: for a perturbation of size $\delta$ and a flow with Lipschitz constant $\Lambda$ over a span $t$, Grönwall bounds the trajectory error by $\delta(\mathrm{e}^{\Lambda t} - 1)/\Lambda$ however the time integration is done. Refining the step, or raising order, pays only until the time error reaches that floor. Where Heun's docstring reports a crossover in resolution, this scheme has none: at third order under the advective-CFL loop the time error falls as $\Delta x^{3}$ — the same rate as the default CatmullRom floor's $\Delta x^{d+1}$ — so their ratio is set by prefactors alone, and measured on a band-limited field at $N = 32$–$128$ the floor stays two to three orders of magnitude below the time error. At CFL steps the interpolant never limits an Adams–Bashforth trajectory, and a wider stencil buys nothing; only a $\Delta t$ cut well below the CFL value surfaces the floor.

The floor is set by the interpolant's polynomial reproduction degree, not its smoothness class — measured here, raising the degree at fixed $C^1$ lowered it fifty-fold, while varying the smoothness at fixed degree left the time convergence unchanged. Raise the degree when the floor is what limits you; smoothness buys something different, namely readouts that differentiate the interpolant, such as acceleration (Lalescu, Teaca & Carati 2010).

References

  • Lalescu, C. C., Bramas, B., Rampp, M. & Wilczek, M. (2022). An efficient particle tracking algorithm for large-scale parallel pseudo-spectral simulations of turbulence. Comput. Phys. Commun. 278, 108406.
  • Lalescu, C. C., Teaca, B. & Carati, D. (2010). Implementation of high order spline interpolations for tracking test particles in discretized fields. J. Comput. Phys. 229(17), 5862–5869.

GBGHomogeneousTurbulence.Particles.ParticleIntegratorBuffers — Type
ParticleIntegratorBuffers

The per-step storage a particle integration scheme computes in, sized to a tracer set and allocated once, so advancing the tracers allocates nothing. Build it with allocate_buffers(scheme, tracers, cache), which allocates exactly what scheme needs and nothing more; a run builds it for you.

This storage belongs to the scheme, not to the trajectory — which is why it lives here rather than in Tracers. One type serves every scheme, because the storage sets nest: a multistep scheme uses the predictor arrays for its Heun starting steps only, and adds two order-element host vectors for its weight solve.

The past Lagrangian samples a multistep scheme integrates over are not held here. They are deposited observables — measurements of the velocity along the trajectory — so they live in the ObservablesCache beside the current sample they extend, which is what lets particles_modified! invalidate the whole history when the tracers are repositioned.

Fields

  • predictor — the (M, 3) predicted positions of the $M$ tracers, which no tracer ever occupies.
  • predictor_points — a PointSet wrapping predictor.
  • velocity_predictor — the velocity interpolated at the predicted positions. It is reachable like any field of this type, but it is a scheme intermediate rather than a sample of the flow at any instant, so nothing in the package offers it as one: read velocity_at_particles for the Lagrangian sample.
  • cache — the run's ObservablesCache: the start-of-step sample and any multistep history are its slots.
  • weights, nodes — the order-element host scratch of a multistep weight solve; empty for a one-step scheme.

The tracking loop

The steps of Lagrangian tracking: record the flow velocity where each tracer currently sits, advance the tracers once the fields have moved, then read any physical field at the particle positions for the Lagrangian statistics. Recording and pushing are two verbs because Heun needs the velocity at both ends of the step: the run records the sample at the iteration's end, off the just-deposited velocity, and the next iteration's advect! reads it back as the first half of its pair.

GBGHomogeneousTurbulence.Particles.advect! — Function
advect!(scheme, tracers, velocity_end, domain, buffers, dt;
        traversal = nothing) -> tracers

Advance the positions of a tracer set by one step, in place.

Arguments

  • scheme — the particle integration scheme, an AbstractParticleIntegrator.
  • tracers — the tracer set whose positions advance.
  • velocity_end — the end-of-step velocity field $\boldsymbol{u}(t_{n+1})$ in physical representation.
  • domain — the FixedDomain, which supplies the box side the positions are wrapped into.
  • buffers — the scheme's working storage, the ParticleIntegratorBuffers that allocate_buffers builds for it.
  • dt — the step size $\Delta t$.
  • traversal = nothing — a ParticleTraversal, to gather the velocity in its memory-locality order; nothing gathers in tracer order, with identical values.

Under Heun, whose docstring gives the update, the scheme is Heun-in-time on the velocity at the two ends of the step — the start-of-step values the previous iteration's closing particle deposit stored, and velocity_end.

Every push also advances the cache's particles epoch, the version of the positions, so a read of the previous velocity sample throws as stale until the particle deposit closing the iteration refreshes it. A hand-run loop gets the same protection as a run.

Under AdamsBashforth, whose docstring gives the update, the position update integrates over the deposited samples instead of interpolating a second time. The first $K - 1$ pushes, with $K$ the order, have no history yet and are taken under Heun; velocity_end feeds only those bootstrap pushes.

The start-of-step velocity is read, never recomputed

The start-of-step velocity $\boldsymbol{v}_1$ comes from the cache's stored velocity at the particles, not recomputed here: it must hold $\boldsymbol{u}(t_n, \boldsymbol{X}(t_n))$, deposited by the particle form of deposit! at the previous iteration's end. The run's advance! checks that it is current before each push; a hand-run loop must make that deposit itself between advances.

GBGHomogeneousTurbulence.Particles.restart! — Function
restart!(scheme, buffers) -> buffers

Discard whatever history buffers holds for the particle integration scheme scheme, so the next advect! starts that scheme from scratch.

Call it whenever the tracer positions are changed from outside the iteration — a reseed, a hand-written correction, any direct write to the tracer storage. A one-step scheme carries no history and this does nothing; a multistep scheme carries Lagrangian samples taken along the trajectory just abandoned, and integrating over those would blend the old path with the new one. This is an in-memory reset of one scheme's history, not a checkpoint verb — restoring a saved run is the job of read_simulation.

The Simulation form of particles_modified! calls this for you, after announcing the reposition to the observables cache. Its bare-cache form clears only the sample history the cache itself holds and cannot dispatch here — so a hand-run loop that announces to the cache alone must also call this; a scheme's own per-step buffers beyond that history are reached only this way.

GBGHomogeneousTurbulence.Particles.history_depth — Function
history_depth(scheme) -> Int

How many Lagrangian samples scheme must be able to look back over, counting the current one.

A run reads this to size the sample history its ObservablesCache carries. A one-step scheme answers 1 and needs no history stored; an order-step method answers order.

The traversal order

The memory-locality order the gathers visit the tracers in — a value-preserving accelerator: the interpolated values are bit-identical with or without it, only the visiting order changes. A run builds and refreshes it for you (the traversal_mode of a ParticleTracking); the type and its rebuild verb are here for a caller driving the tracking loop by hand, or refreshing on a chosen cadence from a run! callback.

GBGHomogeneousTurbulence.Particles.ParticleTraversal — Type
ParticleTraversal(domain, tracers; automatic = true)

The memory-locality order in which a field is gathered at the tracers — a PointTraversalOrder over the tracer set tracers on the grid of domain (a FixedDomain), together with the scratch that lets it be rebuilt in place. Tracers seeded at random, or mixed by the flow, visit the grid in no order at all, so each interpolation stencil is a cache miss; visiting them tile-by-tile turns the gather into a sweep, and GBGPeriodicFields' interpolate! accepts such an order through its traversal keyword. The order only reorders the visits — it changes no value, so a run with and without it produces bitwise-identical trajectories and samples.

A run builds one for you: the traversal_mode of its ParticleTracking decides whether, and whether the run or the caller rebuilds it. Building it by hand belongs with a hand-run loop, where the ParticleTraversal itself is passed on to advect!, the particle form of deposit! and interpolate_at_particles! through their traversal keyword; on a run, that is sim.particle_traversal.

Arguments

  • domain — the FixedDomain whose grid the tiles are laid over.
  • tracers — the Tracers whose positions are ordered; the order is sized to their count and built from their current positions.
  • automatic = true — whether a run rebuilds the order every iteration (true) or leaves the rebuilding to the caller, through rebuild_traversal! (false). A rebuild costs a small fraction of the gather it accelerates, so every iteration is the default; a stale order is never wrong, only progressively less useful as the flow mixes the tracers away from it.
One order serves every gather of the step

GBGPeriodicFields accepts any same-length order for a point set of the same count, so the one order built from the tracer positions is also passed to the gather at the predicted positions a Heun step makes; those sit a step's displacement from the tracers, well inside the tiles the order groups.

Fields

  • order — the PointTraversalOrder: one Int32 index per tracer, a permutation of the visits.
  • scratch — the PointTraversalOrderScratch the in-place rebuild sorts in: the per-tracer tile keys and the per-tile counts and offsets.
  • automatic — whether a run rebuilds the order every iteration.

GBGHomogeneousTurbulence.Particles.rebuild_traversal! — Function
rebuild_traversal!(traversal, domain, tracers) -> traversal
rebuild_traversal!(sim) -> sim

Rebuild the tracer traversal order from the current tracer positions, in place.

Arguments

  • traversal — the ParticleTraversal to rebuild.
  • domain — the FixedDomain whose grid the order is taken on.
  • tracers — the tracer set whose positions are ordered.
  • sim — a run (Simulation), in the second form: the traversal it carries as sim.particle_traversal is rebuilt.

Wiring tracers into a run

Give Simulation a ParticleTracking and the run carries a tracer set: advance! pushes it every iteration and records the Lagrangian sample, so the reads below are always current between iterations.

sim = Simulation(grid_points_per_axis = 64, particles = ParticleTracking(number_of_particles = 4096))
warmup!(sim)
advance!(sim)

point_positions(sim.tracers.positions)     # (M, 3) positions, via GBGPeriodicFields
velocity_at_particles(sim.cache)  # u(tₙ, X(tₙ)) — the Lagrangian sample; throws if stale
out = new_vector_point_values(sim.tracers)   # allocate once, then reuse
interpolate_at_particles!(out, velocity_physical(sim.cache), sim.tracers)
