Memory footprint on a GPU

A run goes on a GPU through the array_family keyword of Simulation: CuArray for an NVIDIA card, with CUDA added to your environment, or ROCArray for an AMD card, with AMDGPU. Its element_type keyword sets the precision. This page answers the question a GPU run meets first, whether a grid fits on the card; it also describes how CUDA's unified memory lets a run outgrow the card. Everything else about driving a device, from writing efficient device code to the vendors' pitfalls, is on the field library GBGPeriodicFields's Running on a GPU page.

What a run keeps in memory

The table gives everything a Simulation holds: the state, the integrator's per-step storage (IntegratorBuffers), the generator's workspace for the right-hand side, the ObservablesCache, and the domain's precomputed spectral multipliers, with every setting not named in a column at its default. On a grid of $N^3$ points, $N$ even, that storage is a cubic polynomial in $N$. The bytes per grid point are its leading coefficient, and the three right-hand columns evaluate the whole polynomial, lower-order terms included.

The table holds for every forcing, for HouLi() as for TwoThirds(), and for the integrators IFLowStorageRK3, IFLowStorageRK4 and IFSSPRK3. The IFHeun integrator and HouLi(materialized = true), which stores the filter per mode instead of re-evaluating it, each add storage of their own. Tracers are cheap next to the fields: with the default Heun scheme a Float32 run holds 61 bytes per tracer and a Float64 run 109. The package's test suite derives the table and every number in this paragraph from the code, so a change to the code that moves one of them fails the suite.

On a GPU two costs come on top, and neither is in the table: the CUDA context, fixed in size, and the FFT library's (cuFFT's) workspace. On an RTX 5070 Ti the whole footprint on the card measured 5 to 38 bytes per grid point above the table across its eight rows, the allocator's rounding included. That figure was measured once, on one card, and nothing checks it.

Fields larger than GPU memory

CUDA.jl can allocate every CuArray in unified memory, which the driver pages between the GPU and host RAM, so a run whose fields exceed the card runs unchanged as long as the excess fits in host RAM. The setting is made once, in the project the run is started from; the call that makes it, the two entries it writes, and the spelling that leaves it silently off are on the field library's page, under Fields larger than GPU memory. AMD's AMDGPU has no unified memory, so a run on a ROCm card has to fit in the card's memory.

The package itself needs no change. It never chooses a memory kind where it allocates, so every array a run holds follows the setting: the state, the scalar, the tracers, and a run restored by read_simulation with array_family = CuArray. Each of those was checked once, on one CUDA card. To confirm the setting took effect in your own run, a Simulation sim, read the memory kind of its velocity:

using CUDA
using GBGPeriodicFields: field_data

CUDA.is_unified(field_data(sim.state.velocity_spectral))   # true once the setting is on

A displayed Simulation shows CuArray either way, so this call is the check.

Unified memory changes more than where the fields live

The setting covers every array the Julia process allocates, not one run's fields. The cuFFT workspace stays in device memory, so it still has to fit on the card. Unified arrays ignore CUDA.allowscalar(false), so a scalar index into a unified array runs, slowly, instead of raising an error; develop in device memory. The package's own test suite runs only on the CPU. The field library's GPU test suites, one of which runs in unified memory, cover the operations a run is built from, not a run.

What spilling over costs depends on the link between the GPU and host memory and on the access pattern. On a PCIe host the field library measured a $512^3$ Float64 transform round trip at about 8% slower in unified memory while every field fit on the card, and about 2.9 times as long once the fields in use totalled 1.3 times the card's memory. A time step is not a transform round trip, and no run of this package has been timed in unified memory. On Grace Hopper (GH200) the cost is unmeasured: host memory sits on a much faster link there, and the setting selects memory that migrates between host and GPU, not the GPU's direct access to host memory that GH200 also supports. CUDA.jl prefetches a unified array before each launch only when the process sees exactly one GPU, so a job restricted to its own GPU and one that sees every GPU on the node page in different regimes. Time a few steps at the target grid, in the job configuration the campaign will use, before planning on it.
