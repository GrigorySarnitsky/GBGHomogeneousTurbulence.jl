Derived quantities

A run integrates the velocity $\boldsymbol{u}$ and the passive scalar $\varphi$, and no other field. It holds them in spectral representation as $\hat{\boldsymbol{u}}$ and $\hat\varphi$, and it knows their values only at the discrete times $t_0, t_1, t_2, \dots$ at which its steps begin and end. Together they are the state. Tracer positions are carried forward too, by their own equation, but they are not fields and not part of the state.

Everything else a run computes is a derived quantity: something the state at one of those times determines completely. The velocity in physical representation is one. So are the vorticity, the advection terms, the velocity sampled along a particle trajectory, and the kinetic energy — a field in either representation, a set of values at particle positions, or a single number. Because the state determines them, a run can rebuild any of them exactly. To hold one is to retain it between steps for you to read, rather than rebuild it when you ask.

This package makes one choice about that, and states it here rather than deriving it: requesting a quantity adds nothing to what a run's step cycle computes or moves. The cycle is everything a run does to get from $t_n$ to $t_{n+1}$ — measuring the timestep, recording the tracer velocities, taking the step, advecting the particles, and whatever the loop measures for its own stopping test. What it moves is counted in passes over the grid. The opposite choice is defensible: a run could do extra work in its cycle so that a request became free at the point of reading. This one does not, so what a cycle costs is fixed by how you configured the run and by the stopping condition you gave it, and never by what you later ask to see.

Holding a quantity therefore gains you no information, and the choice is a narrow one. This page answers what is left of it:

  2. What guarantee does a held value carry? (§2)
  3. What does holding one cost, and what do you choose? (§3)
  4. Which does this package's cycle compute, and which does a run hold? (§4 establishes the system; §5 applies §§1 and 3 to it)
  5. How do you read one, request one, and report a change you made? (§6)

Sections 1–5 describe the design. Where the package does not yet meet a claim it is marked (not yet — §7), and §7 says why each gap stands.

1. Which quantities a run may hold

Two questions decide it, and they are different questions. The first asks whether a quantity is the kind of thing this page is about. The second asks whether a run may hold one that is.

Is it a derived quantity at all?

A derived quantity is fixed by the state at a single $t_n$. Two ways to fall outside that:

  • It depends on more than the state. A quantity that also depends on the step size $\Delta t$, on a forcing's internal variables — the Ornstein–Uhlenbeck state of a stochastic source, say — or on the coefficients of the time-stepping scheme is not determined by the state, so no amount of state will rebuild it.
  • It is fixed at some other instant. A Runge–Kutta stage value is determined by the state and the discretization, so it is not the flow at any instant. For a quantity carried along a trajectory, the particle's position is one of its arguments: the velocity at a predicted position is evaluated where no particle is.

A quantity failing the second way fails the first as well — a stage value depends on $\Delta t$ — so where both apply, the more specific reason is the one this page gives.

May a run hold it?

Here the choice stated above does the work, and it does so twice, in two different currencies.

In arithmetic: a run holds only what its cycle computes anyway. A run refreshes a held value from its cycle, not from your read (not yet — §7). So a quantity that nothing in the cycle computes could be held only by making the cycle compute it — which is precisely the work a request may not add.

In passes over the grid: a run holds only what its cycle already has whole. This is the same choice in the second currency, and §3 states it where the price makes it legible.

2. What a held value guarantees

Rebuilding says holding gains you nothing. This section is the other half: holding loses you nothing either, because a read never returns a value built from a superseded state.

The cycle refreshes a held field at its end, from the state it has just produced (not yet — §7). That recovery is free, and conditionally so: it is the one the next cycle's first stage would have performed, moved earlier, which costs nothing provided another cycle follows and its first stage reads what is there. At the end of a run the last refresh has no successor to donate it to.

Only you can supersede a held value afterwards, by changing the state outside a cycle — reseeding an initial condition, applying a filter. You report that by calling resolved_fields_modified!, which advances the run's counter; a read compares that counter against the stamp each held value carries and rebuilds when they differ. The routines that change the state as part of their normal work report it themselves. Given the refresh above, this path is exercised only after a change of your own.

Nothing refreshes a held value in mid-cycle, because in mid-cycle there is nothing to refresh: an array holding a quantity for you may be the array the cycle is working in (§3 prices this), and while a cycle runs it carries stage values. A run refuses such a read rather than answering it with one (not yet — §7).

A held number is current at the instant its cycle measured it, which is not always the instant you read. Under run! the loop measures the maximum speed at $t_n$, before the step, because the timestep control needs it to choose $\Delta t$. It measures $\varepsilon$ and $k$ there too when the run is budgeted in turnovers or stopped on a condition, and not otherwise. Their order within the iteration decides who reads them free: the stopping test runs after $\varepsilon$ and before the other two, so it reads $\varepsilon$ at no cost and would rebuild the rest. A callback fires once the step has completed, so it finds all three at a superseded state — a rebuild of one reduction each, and for the maximum speed a velocity recovery the next cycle would have performed anyway.

3. What holding costs, and what you choose

Holding never changes the number of Fourier transforms a cycle performs (§4.3 establishes this), so choosing to hold something is a memory decision and never a time decision. Memory is charged at one of three levels:

what the cycle does with the valuewhat holding it costs you
has it whole, and does not need that array againnothing
has it whole, but needs that array againone array, for the cycle to write its next result elsewhere
never has it wholeone array, and a grid-sized write the cycle does not already perform

A vector field on the grid is $3N^{3}$ reals — 384 MiB at $N = 256$ in double precision, 192 MiB in single. A velocity-only run under a mask rule already carries ten vector-shaped fields, five in each representation, so about 3.8 GiB at that size before any scalar-shaped register.

A run accepts the first two levels and refuses the third. The refusal is not a judgement about magnitude; it is the choice of the opening in its second currency. A value the cycle forms only piecewise, inside a single traversal, would have to be written out for you, and that write is a pass the cycle does not already perform. Calling a value materialized when the cycle has it whole somewhere, this is the second half of §1: a run holds only what its cycle already materializes.

The clearest instance is the integrand of a fused reduction. Computing $k$ sums $\lvert\hat{\boldsymbol{u}}(\boldsymbol{\kappa})\rvert^{2}$ over wavenumbers in one traversal, forming every value and keeping none. Written out, those values are twice the energy density mode by mode — a field in its own right, and one an anisotropy study wants. Materializing it costs one grid-sized write and no new arithmetic. It is not the energy spectrum: $E(\kappa)$ is half the sum of those values over each wavenumber shell, and computing it needs a further binning pass.

What you choose

You request the fields and trajectory samples you want held when you configure the run. A quantity you do not request is not held, and reading it is an error rather than a quiet rebuild — which is what makes the memory a run occupies follow from the call that configured it, instead of from which diagnostic you happened to write. Which level a field sits at is a property of the cycle, not something you can know in advance; §5 gives it for the configuration §4 fixes.

A number the cycle already computes is held without asking, and stored where the cycle computes it rather than recomputed at the end. Keeping $O(1)$ of storage is not worth a decision, so a run does not make you take one. Which numbers a cycle computes depends on the run you asked for: a turnover-budgeted or condition-stopped run! measures $\varepsilon$ and $k$ each iteration, an adaptive timestep measures the maximum speed, and a warmup! watching for stationarity measures the derivative skewness at its sampling cadence — and the scalar variance too, when the run carries a forced scalar. (not yet — §7)

4. The system this package solves, and what its cycle does

The rules above turn on what a cycle computes, what it has whole, and what it costs. This section establishes those three for one system in one configuration: a mask dealiasing rule, a three-stage scheme, the default rescaling velocity forcing, and an adaptive timestep. Those are the axes that fix a cycle's work — together with the stopping condition, which decides which reductions the loop performs. A request is not among them.

4.1 The equations

The package advances the incompressible Navier–Stokes equations in rotational form on a triple-periodic box, with a passive scalar and tracer particles. Writing the convective term through

\[(\boldsymbol{u}\cdot\nabla)\boldsymbol{u} = \nabla\big(\tfrac{1}{2}\lvert\boldsymbol{u}\rvert^{2}\big) - \boldsymbol{u}\times\boldsymbol{\omega}\]

and letting the Leray–Helmholtz projection $\mathbb P$ onto divergence-free fields absorb both the pressure and the gradient $\nabla(\tfrac{1}{2}\lvert\boldsymbol{u}\rvert^{2})$, the system reads

\[\begin{aligned} \frac{\partial \boldsymbol{u}}{\partial t} &= \mathbb P\,(\boldsymbol{u}\times\boldsymbol{\omega}) + \nu\nabla^{2}\boldsymbol{u} + \boldsymbol{f}, &\qquad \nabla\cdot\boldsymbol{u} &= 0, \\[4pt] \frac{\partial \varphi}{\partial t} &= -\nabla\cdot(\boldsymbol{u}\varphi) + \varkappa\nabla^{2}\varphi + f_\varphi, \\[4pt] \frac{\mathrm{d}\boldsymbol{X}}{\mathrm{d}t} &= \boldsymbol{u}(t, \boldsymbol{X}(t)), \end{aligned}\]

with $\boldsymbol{\omega} = \nabla\times\boldsymbol{u}$ the vorticity, $\nu$ the kinematic viscosity, $\varkappa = \nu/\mathrm{Sc}$ the scalar diffusivity, $\boldsymbol{f}$ and $f_\varphi$ the forcings, and $\boldsymbol{X}(t)$ a tracer position. No projection acts on $\boldsymbol{f}$ because every velocity forcing the package provides is already divergence-free — one proportional to the field scales a divergence-free field mode by mode, and a stochastic source is projected as it is drawn. The scalar advection is written in conservative form, which holds the $\boldsymbol{\kappa} = 0$ tendency at exactly zero and fixes the split of transforms printed below.

4.2 How a step treats each term

  • The quadratic terms $\mathbb P(\boldsymbol{u}\times\boldsymbol{\omega})$ and $-\nabla\cdot(\boldsymbol{u}\varphi)$: the step evaluates them as fields.
  • The viscous terms $\nu\nabla^{2}\boldsymbol{u}$ and $\varkappa\nabla^{2}\varphi$: the step never forms them at all. Being diagonal in the spectral representation they integrate exactly, and the step multiplies the field by $\mathcal E(\boldsymbol{\kappa}) = \exp\big((A(\boldsymbol{\kappa}) - D\lvert\boldsymbol{\kappa}\rvert^{2})\tau\big)$ instead, with $D = \nu$ or $\varkappa$, $A(\boldsymbol{\kappa})$ the rate of a forcing proportional to the field, and $\tau$ the sub-interval a stage advances.
  • A forcing arrives by one of three routes. One proportional to the field folds its rate $A(\boldsymbol{\kappa})$ into that exponential — the rate array exists, the product $A(\boldsymbol{\kappa})\hat{\boldsymbol{u}}$ never does. An additive source is added to the right-hand side at each stage. A rescaling is applied to the completed step, as a map on the state rather than a term in any equation; the default velocity forcing is of this kind, holding the kinetic energy fixed by rescaling a band of modes.

4.3 What a cycle costs in transforms

The state lives in spectral representation, where derivatives are multiplications and the projection acts wavenumber by wavenumber. A product of two fields is a convolution there, so each quadratic term is evaluated the pseudospectral way. Under a mask rule, one evaluation of the velocity term takes five operations. The evaluation

  1. recovers $\boldsymbol{u}$ in physical representation — 3 inverse transforms;
  2. forms $\hat{\boldsymbol{\omega}} = \mathrm i\boldsymbol{\kappa}\times\hat{\boldsymbol{u}}$ and recovers $\boldsymbol{\omega}$ — 3 inverse transforms;
  3. multiplies the two pointwise into a third array, giving the Lamb vector $\boldsymbol{u}\times\boldsymbol{\omega}$;
  4. transforms that array back — 3 forward transforms;
  5. applies $\mathbb P$ and the mask, both per-wavenumber multiplications.

How a run removes the aliasing the pointwise product introduced is its dealiasing rule, and the rule changes the count. TwoThirds and HouLi are mask rules: each discards or tapers the aliased wavenumbers in one per-wavenumber multiplication. PhaseShift instead evaluates the term a second time on a half-cell-displaced grid and averages the two, cancelling the aliases rather than filtering them, at twice the transforms — and, with the scalar, nine inverse transforms more than twice, because the scalar term re-recovers a displaced velocity the velocity term has already built.

dealiasing rulevelocity onlywith the scalar
TwoThirds, HouLi18 inverse, 9 forward21 inverse, 18 forward
PhaseShift36 inverse, 18 forward51 inverse, 36 forward

None of these counts depends on what a run holds. The end-of-step refresh of §2 replaces the next cycle's first-stage recovery rather than adding to it, so a held field is recovered once per cycle whether or not you hold it. These transforms carry essentially all of the arithmetic — one scalar transform costs of order $10^{2}$ operations per grid point, while each pointwise operation above costs of order ten.

4.4 What a cycle needs at once, and what the tracers sample

Operation 3 writes the pointwise product into an array of its own, so the vorticity survives the evaluation: a velocity-only evaluation under a mask rule needs three vector arrays in physical representation at once — one carrying $\boldsymbol{u}$, one carrying $\boldsymbol{\omega}$, one receiving their product. Writing the product over the vorticity instead would need two, which is the second cost level of §3 in the concrete; that saving is unavailable today, because the backend's cross product guards against writing into one of its own operands by allocating a temporary and copying back, which costs more than the array it would save.

A cycle advances each tracer position with a two-stage scheme. It samples the velocity at the start of the step, at the particle's position, and at the end of the step, at a predicted position the particle never reaches. Both samples are $M\times3$ arrays for $M$ particles, interpolated from the physical velocity field with the tracer set's interpolation scheme — a Catmull–Rom spline by default, so the sampled velocity is continuously differentiable along a trajectory.

The state and the tracer positions are always present. Tracers consume a derived field and produce values at points; they never hold a field. The table below covers what a cycle computes from the state.

5.1 The pressure is absent, dissipation names three objects, and only one tracer sample samples the flow

The pressure never appears. The projection absorbs it and no stage computes it. Recovering it means solving its Poisson equation separately — and what the rotational form suppresses is the total head $p + \tfrac{1}{2}\lvert\boldsymbol{u}\rvert^{2}$ per unit density, so such a solve returns that combination, from which $\tfrac{1}{2}\lvert\boldsymbol{u}\rvert^{2}$ must be subtracted.

Three different objects are called dissipation. The viscous term $\nu\nabla^{2}\boldsymbol{u}$ is one, and §4.2 shows why no array holds it. The local dissipation $\nu\lvert\boldsymbol{\omega}\rvert^{2}(\boldsymbol{x})$ is an ordinary field, which you can form pointwise from a held vorticity. The dissipation rate $\varepsilon = \nu\langle\lvert\boldsymbol{\omega}\rvert^{2}\rangle$ is a single number, which a run obtains by summing over wavenumbers without building any field, and is what dissipation returns.

Only one of the two tracer velocity samples is a sample of the flow. The start-of-step sample $\boldsymbol{u}(t_n, \boldsymbol{X}(t_n))$ is the velocity where the particle is, when it is there, and is what a Lagrangian velocity statistic accumulates. The second is taken at a predicted position the particle never reaches — it differs from the endpoint by $\mathcal O(\Delta t^{2})$ — and exists only to give the position update its second-order accuracy. It carries the units of a velocity and is a stage value of the integrator, so a run does not expose it.

6. Reading a held quantity, requesting one, and reporting a change

These calls are provisional

How you assemble and drive a run is not settled, so the calls below may change. The rules of §§1–5 hold whatever they become.

You read the two held fields that exist today from a run:

using GBGIsotropicTurbulence

sim = Simulation(grid_points_per_axis = 64, viscosity = 0.005)
advance!(sim; dt = 1e-3)

u = physical_velocity(sim)      # the velocity in physical representation, at the new time
ω = physical_vorticity(sim)     # the vorticity, likewise

physical_velocity and physical_vorticity return the held field when it matches the present state and rebuild it first otherwise. The velocity along each trajectory comes from tracer_velocities, and sample! interpolates any physical field at the particle positions.

Which quantities a run holds is fixed when its DerivedFields is constructed, through the charts keyword — one Symbol per quantity:

domain  = FixedDomain(64, 2π; dealiasing = TwoThirds(), element_type = Float64, array_type = Array)
derived = DerivedFields(domain; charts = (:velocity, :vorticity))

(not yet — §7) A Simulation builds its own DerivedFields and takes no such argument, so this choice cannot yet be made through the front door, and both fields are always held.

After you change the state outside the stepping routine — reseeding, filtering — call resolved_fields_modified!; the resolved fields are the two integrated fields of the opening, not a filtered subset of the scales. That advances the counter of §2, so a run rebuilds every held field on the next read of it. The velocity along a trajectory is not checked against that counter (not yet — §7).

7. Where the package does not yet meet the design

Today a run holds the velocity, the vorticity, and the velocity along each trajectory. Every other row of §5 is design. The gaps, and why each stands:

  • A run builds a held field when you first read it, not at the end of the preceding cycle. The transform count is the same either way, since the next cycle's first stage consumes what a read builds; what the eager refresh buys is a read between cycles that computes nothing, and the epoch bookkeeping is written for invalidation rather than for deposit.
  • A held field and the array a cycle works in are separate arrays, so requesting a field costs a new allocation rather than a forgone overwrite. Sharing them requires the mid-cycle read to be refused, which is not yet implemented.
  • A run holds no numbers, so the reductions its loop already performs are discarded and a diagnostic that wants one repeats it.
  • A Simulation passes no charts argument through, so the requesting rule is reachable only by assembling a run's pieces directly. There is also no narrower set to request today: a step reads both fields at its first stage, so dropping either would stop the run.
  • The velocity along a trajectory is held with the particle set, and whether it is current is stated in its documentation rather than checked against the counter of §2.

The decisions behind each are in the architecture notes.
