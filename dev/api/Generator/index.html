Generator

GBGIsotropicTurbulence.Generator — Module
Generator

The flow's equations of motion — the incompressible Navier–Stokes right-hand side in rotational form (the dealiased, Leray-projected nonlinear term), the passive-scalar advection, and the exact viscous integrating factor.

Its contents (each formula lives in the operation's own docstring):

  • FlowConditions — the physical conditions the right-hand side is built from (the viscosity, the Schmidt number, the forcings).
  • ResolvedGenerator — the generator as one value: the conditions bundled with the assembly scratch its evaluations write through, consumed by a scheme through the protocol below.
  • prepare! — open a step: advance the forcings' internal state and arm the linear rates.
  • velocity_rhs!, scalar_rhs! — assemble the explicit right-hand sides (the dealiased, Leray-projected momentum term and the scalar advection, each plus its additive forcing source) at a stage state.
  • velocity_integrating_factor, scalar_integrating_factor — supply each field's exact linear subflow (the viscous/diffusive integrating factor, with any linear forcing rate folded in).
  • finalize! — close a step: apply the post-step forcing projections to the advanced state.

The assemblies recover displaced fields in physical representation with the four-argument, source-preserving form (the extra argument is a scratch field the transform consumes in the source's place) of to_physical! and with vorticity_physical!.

Flow conditions

The physical conditions the generator is built from — viscosity, Schmidt number, and the velocity and scalar forcings.

GBGIsotropicTurbulence.Generator.FlowConditions — Type
FlowConditions(; viscosity, schmidt, velocity_forcing, scalar_forcing)

The physical conditions the generator is built from — the kinematic viscosity $\nu$ (viscosity; the Reynolds number is $\mathrm{Re} = 1/\nu$), the Schmidt number $\mathrm{Sc}$ (schmidt; the scalar diffusivity is $\varkappa = \nu/\mathrm{Sc}$), and the velocity and scalar forcing strategies (velocity_forcing, scalar_forcing , both AbstractForcing ). Consumed by the time step (step!).

Arguments

All keyword, all required:

  • viscosity — the kinematic viscosity $\nu$.
  • schmidt — the Schmidt number $\mathrm{Sc}$.
  • velocity_forcing, scalar_forcing — the forcing strategies for the velocity and the scalar, each an AbstractForcing (pass NoForcing() to leave a field undriven).

Fields

The plain constructor FlowConditions(viscosity, schmidt, velocity_forcing, scalar_forcing) takes the four fields directly, in this order.

  • viscosity, schmidt — the kinematic viscosity $\nu$ and the Schmidt number $\mathrm{Sc}$ (both Float64).
  • velocity_forcing, scalar_forcing — the velocity and scalar forcing strategies, each an AbstractForcing.

The generator as one value

The right-hand side as one object — the conditions bundled with the assembly scratch its evaluations write through. A time-marching scheme consumes it only through the protocol below.

GBGIsotropicTurbulence.Generator.ResolvedGenerator — Type
ResolvedGenerator(domain, conditions; scalar = false)

The flow's generator as one value a scheme can hold. It carries the FlowConditions parameter record together with the assembly scratch its evaluations write through: the quadratic-product fields, the per-mode forcing-rate arrays, and — when the domain dealiases by PhaseShift — the displaced-evaluation buffers.

That scratch is the generator's own storage, distinct from the run's observables cache. The two do meet at one point: the physical quadratic products are formed in place over the cache's arrays, the Lamb vector over the vorticity slot and the scalar flux over the velocity slot, so no product field in physical representation is allocated anywhere.

A time-marching scheme consumes the generator through a fixed protocol: prepare! once per step, velocity_rhs! / scalar_rhs! at each stage state, velocity_integrating_factor / scalar_integrating_factor for the exact linear subflows, and finalize! after the completed step. The scheme does only stage arithmetic, so it can never assemble the right-hand side from a mismatched intermediate state.

One optimization crosses two verbs

Under PhaseShift, velocity_rhs! leaves the stage's displaced velocity fresh for the same stage's scalar_rhs! to reuse, through the displaced_velocity_fresh flag rather than through either signature. It is opportunistic, never load-bearing: a scalar_rhs! that finds the flag clear rebuilds the displaced velocity itself, value-identically.

Build it on the FixedDomain domain from the conditions; pass scalar = true when the run carries a passive scalar (it allocates the scalar's forcing-rate array, required for a scalar-forced run). The Simulation front door — the convenience constructor that builds every component — builds one for you.

Fields

  • conditions — the FlowConditions parameter record ($\nu$, $\mathrm{Sc}$, the forcings).
  • product_spectral — the quadratic products' spectral image (the transformed Lamb vector $\boldsymbol{u}\times\boldsymbol{\omega}$, or the transformed scalar flux $\boldsymbol{u}\varphi$). In physical representation each product is formed in place over an operand's own array — the Lamb vector over the vorticity's, the flux over the velocity's — so no physical product array exists.
  • phase_shift — the displaced-evaluation scratch and translation kernels (PhaseShift dealiasing only), else nothing.
  • velocity_rate, scalar_rate — the per-mode linear forcing-rate arrays $A(\boldsymbol{\kappa})$. prepare! fills them at the start of each step; a rate that has been filled is one the integrating-factor verbs then return alongside the viscous coefficient, so the forcing rides the exact linear solve instead of being added afterwards. Each is nothing unless that field's forcing declares uses_linear_rate, so a field driven by a post-step projection, a stochastic source, or nothing at all carries no rate storage; scalar_rate is also nothing for a scalar-free generator.
  • displaced_velocity_fresh — whether phase_shift.u_shifted still holds the current stage's displaced velocity, left fresh by velocity_rhs! for the same stage's scalar_rhs! to consume (PhaseShift only; a bare scalar_rhs! finding it stale rebuilds the recovery itself).
The constructor rejects a misdeclared forcing

A forcing that implements set_forcing_rate! without also declaring uses_linear_rate is given no rate array to fill, so its forcing would silently never be applied. Building a ResolvedGenerator around one throws an ArgumentError naming the strategy, rather than letting the run proceed quietly wrong.

The generator protocol

One step of the dynamics, as the scheme sees it: open with prepare!, evaluate the right-hand sides and the exact linear factors at each stage, close with finalize!.

GBGIsotropicTurbulence.Generator.prepare! — Function
prepare!(generator, state, domain, dt)

Open a step of the generator: advance each forcing's internal state once (its per-step prepare_forcing! hook) and arm the per-mode linear forcing rates (fill them, so the factor verbs return them instead of nothing ) (its set_forcing_rate! hook, written into the generator's rate arrays) from the start-of-step state (a ResolvedFields ) over the timestep dt, on the FixedDomain domain. A scheme calls this once before its Runge–Kutta stages; the stage evaluations and the integrating factors then consume what it prepared. Returns generator.

GBGIsotropicTurbulence.Generator.velocity_rhs! — Function
velocity_rhs!(N̂, generator, û, u, ω_consumed, domain)

Assemble the explicit right-hand side of the momentum equation into N̂ — the dealiased, Leray-projected rotational nonlinear term plus any additive forcing source — from the stage velocity û in spectral representation and its physical velocity u and vorticity ω_consumed, on the FixedDomain domain, using the ResolvedGenerator generator's conditions and scratch. The vorticity argument carries _consumed in its name because it is: see the note below.

In physical space the rotational form writes the convective term as the Lamb vector, through the identity

\[(\boldsymbol{u}\cdot\nabla)\boldsymbol{u} = \nabla\big(\tfrac{1}{2}\lvert\boldsymbol{u}\rvert^{2}\big) - \boldsymbol{u}\times\boldsymbol{\omega},\]

so that, with the Leray–Helmholtz projection $\mathbb{P}$ onto divergence-free fields absorbing the pressure and the $\nabla(\tfrac{1}{2}\lvert\boldsymbol{u}\rvert^{2})$ gradient, the momentum equation becomes

\[\partial_t\boldsymbol{u} = \mathbb{P} (\boldsymbol{u}\times\boldsymbol{\omega}) + \nu\nabla^{2}\boldsymbol{u} + \boldsymbol{f}.\]

The term computed is the spectral image of $\mathbb{P} (\boldsymbol{u}\times\boldsymbol{\omega})$, dealiased by the domain's DealiasingStrategy, plus the per-stage additive source of the generator's velocity forcing (its add_forcing_source! hook). A mask strategy (TwoThirds, HouLi) forms the term once from u, ω and multiplies by the low-pass domain.dealias, leaving û unused; PhaseShift forms it twice — from u, ω, and from the fields recovered on a grid displaced by half a cell (using û and the generator's displaced-evaluation scratch) — averages the two to cancel the aliasing, then truncates spherically with domain.dealias.

Two linear pieces are deliberately not in N̂: the viscous term and the exactly-linear part of a forcing are advanced exactly by the integrating factor (velocity_integrating_factor).

`ω_consumed` is read and then overwritten

The Lamb vector is formed in place over the vorticity's array — the backend's cross product may write into one of its operands — so ω_consumed must hold the vorticity on entry and no longer does on return, while u is only read. This is what keeps a product field in physical representation from existing at all; passing a copy instead would cost a resident $N^{3}$ vector, which the footprint invariant forbids.

Which operand is consumed follows the physics, not the argument position: the Lamb vector forms over the vorticity here, and the scalar flux over the velocity in scalar_rhs! — which is why both name the consumed argument rather than leaving a caller to infer it. Only the spectral product scratch remains on the generator, and the operation allocates nothing.

Returns N̂.

GBGIsotropicTurbulence.Generator.scalar_rhs! — Function
scalar_rhs!(N̂, generator, û, φ̂, u_consumed, φ, domain)

Assemble the explicit right-hand side of the passive-scalar equation into N̂ — the dealiased advection term plus any additive forcing source — from the stage velocity û and scalar φ̂ in spectral representation and their physical u_consumed, φ, on the FixedDomain domain, using the ResolvedGenerator generator's conditions and scratch. The velocity argument carries _consumed in its name because it is: see the note below.

In conservative form the advection is $-\nabla\cdot(\boldsymbol{u}\varphi)$ (equal to $-\boldsymbol{u}\cdot\nabla\varphi$ since $\nabla\cdot\boldsymbol{u} = 0$); the conservative form conserves the scalar mean exactly — the divergence has no $\boldsymbol{\kappa}=\boldsymbol{0}$ component, and the dealias kernel domain.dealias (the sharp $2/3$ rule by default) leaves that mode untouched.

It is computed pseudospectrally as $- \operatorname{dealias}\big(\mathrm{i}\boldsymbol{\kappa}\cdot\widehat{\boldsymbol{u}\varphi}\big)$, plus the per-stage additive source of the generator's scalar forcing (its add_forcing_source! hook). The dealiasing strategy controls the aliasing of the quadratic product: a mask strategy (TwoThirds, HouLi) forms the flux once from u_consumed, φ, leaving û and φ̂ unused; PhaseShift instead averages it with the flux recovered on a grid displaced half a cell — using φ̂ and the generator's displaced-evaluation scratch, and reading the displaced velocity the same stage's velocity_rhs! left fresh there (a bare scalar_rhs! with no preceding velocity evaluation rebuilds it from û instead) — before the spherical truncation. The diffusion $\varkappa\nabla^{2}\varphi$ and the exactly-linear part of a forcing are not in N̂: they are advanced exactly by scalar_integrating_factor.

Note

The assembly consumes u_consumed: the flux $\boldsymbol{u}\varphi$ is formed in place over the velocity's array (a pointwise product may write into an operand), so on return u_consumed no longer holds the velocity; φ is only read. As in velocity_rhs!, the consumed argument is fixed by the physics rather than by its position in the signature, and is named for it. Only the spectral product scratch remains on the generator, and the operation allocates nothing.

Returns N̂.

GBGIsotropicTurbulence.Generator.velocity_integrating_factor — Function
velocity_integrating_factor(generator, τ)

The velocity's exact linear subflow over a substep $\tau$ (τ), as the parameters of its exponential rather than a materialized kernel. The linear part of the momentum equation — the diffusion $\partial_t\boldsymbol{u} = \nu\nabla^{2}\boldsymbol{u}$, plus any linear forcing rate $A(\boldsymbol{\kappa})$ that prepare! armed — is solved exactly in spectral representation by the per-mode multiplier

\[\mathcal{E}(\boldsymbol{\kappa}) = \exp\!\big((A(\boldsymbol{\kappa}) - \nu\lvert\boldsymbol{\kappa}\rvert^{2}) \tau\big),\]

with $A = 0$ when no linear forcing is active, so multiplying a field by $\mathcal{E}$ advances its viscous (and linear-forcing) part exactly — machine-exact, with no stability restriction; only a scheme's explicit stage combination carries truncation error. Since the multiplier is the exponential of a radial symbol (plus the armed per-mode rate), a scheme applies it through the backend's fused exponential convolution (exponential_convolve!), which evaluates it per mode from the wavenumber arrays: nothing is built, stored, or swept for it. Accordingly this verb returns the exponential's parameters as a named tuple — $\texttt{coefficient} = -\nu\tau$ (the factor on $\lvert\boldsymbol{\kappa}\rvert^{2}$), $\texttt{offset\_scale} = \tau$ and $\texttt{offset} = \hat A$ (the armed rate field, or nothing when no linear forcing is active) — exactly the arguments the fused exponential takes.

The generator (a ResolvedGenerator) supplies $\nu$ and the armed rate; τ is the sub-interval the stage advances.

GBGIsotropicTurbulence.Generator.scalar_integrating_factor — Function
scalar_integrating_factor(generator, τ)

The passive scalar's exact linear subflow over a substep τ — the same exponential parameters velocity_integrating_factor returns for generator, with the scalar diffusivity $\varkappa = \nu/\mathrm{Sc}$ in place of $\nu$ and the scalar forcing's armed linear rate in place of the velocity's.

GBGIsotropicTurbulence.Generator.finalize! — Function
finalize!(generator, state, domain)

Close a step of the ResolvedGenerator generator: apply each of its forcings' post-step projections (the apply_forcing! hook — e.g. the energy rescale of a BandRescaling ) to the advanced state , velocity first, then the scalar when the run carries one, on the FixedDomain domain. A scheme calls this once after its final stage, so everything that follows the step — the diagnostics, the derived observables, the tracer push — sees the forced end-of-step fields. Returns state.
